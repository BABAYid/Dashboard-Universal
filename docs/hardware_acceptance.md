# Приёмка на железе: что проверить и по каким критериям

Документ для тестов на реальной плате (RK3588 + экран + ESP32 + GPS).
Написано **до** прогонов: так видно, что считается «пройдено», и не
придётся задним числом придумывать критерии под фактический результат.

Артефакты испытаний (в git не кладём — `logs/` в `.gitignore`):

- `logs/metrics.csv` — RSS/CPU/температура/частота/CAN-счётчики/WS-сессии,
  строка раз в минуту;
- `logs/app.log` — структурированный лог (таймстамп, уровень, сообщение,
  ротация 5 МБ → `app.log.1`);
- `logs/load-test.log`, `logs/graphhopper.log`, `logs/tile-server.log`.

## Подготовка (сделано до приезда)

- `tools/metrics.sh` — сбор метрик в CSV (`--once` для проверки).
- `deploy/systemd/dashboard.service` — `Type=notify`, `WatchdogSec=30`,
  `Restart=always`; приложение кормит `WATCHDOG=1` раз в 10 с.
- Структурированные логи: `DASHBOARD_LOG_FILE=/run/dashboard/app.log`.
- `tools/load_test.sh` — сценарий нагрузки на столе (mock): смена экранов,
  шторм WebSocket, churn маршрутов, потеря GPS.
- `tools/desk_demo.sh` — поднять серверы и приборку одним движением.

## Сценарии

### 1. Суточный прогон («просто работает»)

```bash
./tools/load_test.sh 1440        # 24 часа
```

Смотрим в `logs/metrics.csv`:
- RSS за 24 ч вырос **не более чем на 10 %** от значения на 2-й минуте;
- CPU в среднем **≤ 60 %** одного ядра на плате (числовое значение уточним
  на первых часах — важна стабильность, а не пик);
- температура ядра **≤ 75 °C**, частота не «проседает» постоянно на минимум.

### 2. Потеря CAN на 30 секунд

Физически: вынуть CAN-кабель из платы на 30 с, вернуть.
Ожидается: приборка показывает «нет связи» (данные по правилу 1.5 с),
камеры/подсказки гаснут по устареванию, после возврата данные идут без
перезапуска приложения.
Критерий: восстановление **без рестарта** приложения, `bus_off = 0` в
записях `metrics.csv` (если шина вошла в bus-off — отдельный разбор).

### 3. Перезапуск ESP32 на ходу

Перезагрузить блок сбора кнопкой/питанием.
Критерий: восстановление данных ≤ 5 с, `restarts` у блока растёт, но
приборка не падает и не теряет маршрут.

### 4. Шторм WebSocket

```bash
LOAD_WS=20 ./tools/load_test.sh 30
```

Критерий: число сессий в `metrics.csv` возвращается к норме, память не
растёт, ошибок ERROR в `app.log` нет (кроме ожидаемых при обрывах).

### 5. Ночной сбой и авто-восстановление

```bash
sudo systemctl restart dashboard
# имитация падения:
sudo systemctl kill -s KILL dashboard
```

Утром — в журнале `systemctl status dashboard` должна быть запись о
рестарте, `WatchdogSec`-срабатываний — не больше 1 за прогон.
Критерий: сервис поднимается сам, лог не «рвётся» (ротация работает).

### 6. Отклик интерфейса

Критерии (глазами + секундомер):
- нажатие джойстика меняет режим панели **< 100 мс**;
- переключение в навигацию — карта появляется **< 2 с** (WebView
  поднимается лениво — это норма);
- выбор пункта и построение маршрута — **< 1.5 с** (GraphHopper на плате).

### 7. Карта и маршруты

- в навигации подложка, дома, подписи улиц, POI рисуются;
- маршрут от `route_handoff` строится и линия видна;
- `route_state` идёт раз в секунду (Android-клиент это подтверждает);
- `map_subscribe` выключен, пока приборка ведёт маршрут.

## Критерии «пройдено» (сводно)

| Показатель | Порог |
|---|---|
| Старт приложения | ≤ 10 с до первого кадра |
| RSS за 24 ч | рост ≤ 10 % |
| Рестартов сервиса | ≤ 1 за 24 ч |
| CAN `bus_off` | 0 |
| Потеря CAN | восстановление без рестарта |
| Потеря GPS | `valid=false` ≤ 5 с, затем восстановление |
| WebSocket | шторм 20 подключений переживает |
| Отклик джойстика | < 100 мс |
| Температура ядра | ≤ 75 °C |
| ERROR в логе | только ожидаемые (обрывы WS, потеря CAN) |

## Что приложить к отчёту

1. `logs/metrics.csv` (или графики из него: RSS, CPU, температура).
2. Выдержки `logs/app.log` по каждому сценарию.
3. Скриншоты экрана в ключевых состояниях (приборка, навигация,
   плашка манёвра).
4. Заполненная таблица критериев с фактическими значениями.

## Открытые вопросы на момент написания

- Точные пороги CPU/частоты на RK3588 — по первым часам прогона.
- «Перезапуск ESP32» — имитация в mock недоступна; проверяется только на
  железе (на столе — потеря gpsd-эмулятора).
- `bus_off` требует поднятой `can0`; на столе счётчики пустые — норма.
