# LVDS-панель в Linux: как настроить device tree

Поставщик 022A сказал: LVDS настраивают только под Android, для Linux дают
образ с конфигурацией для правки device tree. Значит, панель P1230FHF1MAAA
(12.3″, 1920×720, 2-port LVDS) в Linux мы включаем сами.

Ниже — план, тайминги из даташита и шаблон узлов DT.

---

## 1. Главный лайфхак: взять DT из Android-образа

В Android эта панель **уже работает** — значит, в их DTB есть готовые узлы:
контроллер LVDS, панель с правильными таймингами, подсветка, привязка к VOP.
Это самый короткий и надёжный путь.

Как достать:

```bash
# на образе Android найти dtb (обычно в /boot, /vendor/dtb или пределах boot.img)
# предварительно можно выдернуть из boot.img через unpack_bootimg (AOSP tools)
dtc -I dtb -O dts -o android_board.dts board.dtb

# и посмотреть нужные узлы
grep -n -A25 -i "lvds" android_board.dts | head -80
grep -n -A12 -i "panel" android_board.dts | head -40
grep -n -A12 -i "backlight" android_board.dts | head -30
```

Найденные узлы переносятся в Linux-DT почти один в один: меняются только
`compatible` (в Android могут быть свои имена драйверов), а тайминги,
пины, PWM и включение подсветки остаются те же. Поэтому первым делом
**просите у поставщика их DTS/DTB для Android и для Debian**.

---

## 2. Что просить у поставщика

1. Исходники ядра (`kernel-*.tar.gz`) и U-Boot — то, из чего они собирают.
2. `.dts`, из которого собран **Android**-образ этой платы, и `.dts` для
   **Debian** (если он есть отдельно).
3. Их `build.sh` или команду сборки — иначе не воспроизвести.
4. Версию ядра (`uname -a` на их образе) и включён ли `CONFIG_ROCKCHIP_LVDS`,
   `CONFIG_DRM_PANEL_SIMPLE`, `CONFIG_PWM_*`.
5. Какой PWM/GPIO у них заведён на подсветку (`BL-EN`, `BL-ADJ` — из
   разъёма CON16 на плате) и на питание панели.
6. Точные пины LVDS (пары) и режим: одно- или двухканальный.

---

## 3. Тайминги из даташита

Из `P1230FHF1MAAA_Final spec_Ver2.0.pdf`, раздел 6.1.1 — **на один канал
(link)** двухпортового интерфейса:

| Параметр | Значение (тип.) |
|---|---|
| DCLK (частота пикселей одного канала) | 44.7 МГц |
| Горизонтальный период TH | 1024 Tclk |
| Горизонтальный blanking THB | 64 Tclk |
| Горизонтальная область изображения THD | 960 Tclk |
| Вертикальный период TV | 728 TH |
| Вертикальный blanking TVB | 8 TH |
| Вертикальная область TVD | 720 TH |
| Кадров в секунду | 60 Гц |

Почему 960, а не 1920: панель двухканальная, каждый канал несёт половину
строки. На весь кадр: **1920×720, 60 Гц, DCLK ≈ 89.4 МГц** (44.7 × 2),
горизонтальный период 2048, blanking 128, вертикальный период 728,
blanking 8.

Разбивка blanking на фронт/синхро/задний фронт в тексте даташита не
приведена — она на рисунке 6.2.2 (картинка). **Берите её из вендорского
DTB**, а не угадывайте: неверные porch'и дают «съехавшую» картинку или
артефакты, но не чёрный экран — то есть это легко не заметить на столе.

## 4. Шаблон узлов DT (Linux)

Структура для ядра Rockchip (вендорский BSP, `rockchip_lvds`). Конкретные
имена узлов и меток **сверяйте с вендорским DTS** — они у каждой платы свои.

```dts
/* Подсветка: BL-EN и BL-ADJ приходят с платы на разъём панели */
backlight: backlight {
    compatible = "pwm-backlight";
    pwms = <&pwm? 0 25000 0>;      /* канал PWM, период 25 кГц */
    brightness-levels = <0 4 8 16 32 64 128 255>;
    default-brightness-level = <6>;
    enable-gpios = <&gpio? ? GPIO_ACTIVE_HIGH>;   /* BL-EN */
    power-supply = <&vcc12v_dcin>;               /* питание панели */
};

/* Панель: тайминги из даташита, DCLK 89.4 МГц на два канала */
panel: panel {
    compatible = "panel-simple";     /* или вендорский compatible, если есть */
    power-supply = <&vcc3v3_lcd>;
    enable-gpios = <&gpio? ? GPIO_ACTIVE_HIGH>;   /* RESET/EN, если разведён */
    backlight = <&backlight>;

    display-timings {
        native-mode = <&timing0>;
        timing0: timing0 {
            clock-frequency = <89400000>;
            hactive = <1920>;
            vactive = <720>;
            /* ВАЖНО: porch'и взять из вендорского DTB, не выдумывать */
            hfront-porch = <64>;
            hback-porch  = <64>;
            hsync-len    = <32>;
            vfront-porch = <4>;
            vback-porch  = <4>;
            vsync-len    = <4>;
            hsync-active = <0>;
            vsync-active = <0>;
            de-active    = <1>;
            pixelclk-active = <0>;
        };
    };

    port {
        panel_in_lvds: endpoint {
            remote-endpoint = <&lvds_out_panel>;
        };
    };
};

/* Контроллер LVDS: двухканальный, подключён к видеопорту VOP2 */
lvds: lvds@fde80000 {                 /* адрес и метку сверить с DTS */
    compatible = "rockchip,rk3588-lvds-dual-channel";
    status = "okay";

    ports {
        port@0 {
            lvds_in_vp?: endpoint {
                remote-endpoint = <&vp?_out_lvds>;
            };
        };
        port@1 {
            lvds_out_panel: endpoint {
                remote-endpoint = <&panel_in_lvds>;
            };
        };
    };
};
```

Что обязательно сверить с вендорским DTS (частая причина «не работает»):

1. **Адрес и compatible** контроллера LVDS именно для RK3588 — их два
   варианта (одно- и двухканальный), панель у нас двухканальная.
2. **Маршрут от VOP2**: какой видеопорт (`vp0/vp1/vp2/vp3`) у них завязан на
   LVDS; RK3588 разрешает не любые комбинации — при неправильном маршруте
   экран остаётся чёрным, а в `dmesg` появляется ошибка `vop2` или
   `wait vblank timeout`.
3. **Пины LVDS** (`pinctrl-0`) и их режим — если в их DT есть отдельный
   узел `lvds_pins`, копировать целиком.
4. **Направление сигналов**: `hsync-active`, `vsync-active`, `de-active`,
   `pixelclk-active` — при неверном значении картинка «пляшет» или
   прокручивается.
5. **Питание и включение**: `power-supply`, `enable-gpios`, полярность.

## 5. Проверка по шагам

1. Сначала убедиться, что образ вообще грузится и отдаёт консоль:
   `uname -a`, `dmesg | tail`.
2. Подключить HDMI-монитор (у 022A есть HDMI out) и работать через него —
   так видно, что происходит, даже когда LVDS молчит.
3. После правки DT: `dmesg | grep -iE "lvds|panel|drm|vop"` — драйвер
   должен написать, что нашёл панель и тайминги.
4. `ls /sys/class/drm/` — появился ли разъём/LVDS-коннектор.
5. `modetest -c` (пакет `libdrm-tests`) — список режимов; должен быть
   `1920x720`.
6. Только после этого запускать приборку: `QT_QPA_PLATFORM=eglfs ./appDashboard`.

Признаки «почти работает»: есть подсветка, но экран белый/чёрный — неверные
тайминги или пины; картинка есть, но с полосами — не сходятся скорость или
`pixelclk-active`; мигает — не хватает пропускной способности (не тот режим
LVDS).

---

## 6. Чего ждать по срокам

- Портирование узлов из Android-DTB и запуск LVDS: обычно **день-два** при
  наличии их DTB и серийной консоли.
- Без DTB, только по даташиту: дольше, потому что porch'и и маршрут VOP2
  подбираются по `modetest`/логам итерациями. **Поэтому DTB от Android —
  критичная вещь, её надо получить до начала работ.**
