# Контракт сети: приборка ↔ мультимедиа

Единственный документ, по которому обе стороны (Qt-приборка и Android-блок)
делают сеть. Всё, чего здесь нет, сторонами не придумывается: сначала правка
здесь, потом код.

Версия контракта: **1.0**.

---

## 1. Роли и адреса

| Узел | Адрес | Что делает |
|---|---|---|
| Приборка | `10.0.0.1` | Сервер: данные машины, климат, приём навигации и медиа-запросов, раздача событий джойстика |
| Мультимедиа | `10.0.0.2` | Клиент: спрашивает данные, шлёт навигацию, поднимает WS, **и сам поднимает HTTP-сервер медиа** |

Соединение — прямой патч-корд, статические адреса `10.0.0.0/24`, шлюз не
нужен. DHCP нет. Если IP не поднялся — обе стороны считают, что сети нет, и
продолжают работать каждая сама по себе.

Порты:

| Сервис | Где | Порт |
|---|---|---|
| API приборки | `10.0.0.1` | **8080** |
| Медиа-сервер | `10.0.0.2` | **8080** (тот же номер, но на другом узле — не конфликт) |

---

## 2. Транспорт

- **HTTP/1.1 + WebSocket**. Никакого gRPC и бинарных протоколов: JSON
  читается глазами, проверяется `curl`'ом и логом.
- **HTTP — для запросов по требованию** (состояние машины, климат, команда).
- **WebSocket — для событий и опроса в реальном времени** (джойстик вниз,
  навигация и телеметрия вверх), по одному соединению в обе стороны.
- Кодировка UTF-8, `Content-Type: application/json; charset=utf-8`.
- **Никакой авторизации** в первой версии: кабель изолированный. Поле
  `token` в заголовке зарезервировано на будущее, сервер сейчас его игнорирует.

Базовый путь API: `/api/v1/…`. Несовместимое изменение формата — `/api/v2`,
старый путь живёт, пока клиент не обновится.

---

## 3. Общие правила форматов

1. **Единицы — человеческие, не сырые:** км/ч, °C, вольты, проценты, метры,
   секунды. В пиксели, кБит и «сырые байты CAN» наружу не отдаём.
2. **Нет данных — `null`, а не `0`.** Ноль скорости и «датчик не отвечает» —
   разные вещи, и интерфейс не должен показывать водителю ноль вместо
   «нет данных».
3. **Время** — epoch-миллисекунды UTC, поле `ts`. Отдельно `ageMs` там, где
   важно, сколько данных уже лежит.
4. **Строки — snake_case** (`speed_limit_kmh`, `fan_level`).
5. **Неизвестные поля игнорируются** обеими сторонами: так можно добавлять
   поля, не поднимая версию.
6. Любой ответ содержит `ok: true|false`; при `false` — `error` со строкой
   кода из §8.

## 4. HTTP: приборка (`10.0.0.1:8080`)

### 4.1 `GET /api/v1/car` — данные машины

Полный снимок, до 10 раз в секунду.

```json
{
  "ok": true,
  "ts": 1794012345678,
  "connected": true,
  "data_valid": true,
  "speed_kmh": 63.0,
  "rpm": 1850,
  "gear": "D2",
  "gear_lock": false,
  "fuel_percent": 41.5,
  "engine_temp_c": 88.0,
  "outside_temp_c": 12.0,
  "voltage_v": 13.9,
  "fuel_rate_lph": 7.8,
  "oil_pressure_alarm": false,
  "lights": {
    "left_turn": false, "right_turn": true, "high_beam": false,
    "low_beam": true, "position": true, "fog": false,
    "reverse": false, "brake": false
  },
  "indicators": {
    "check_engine": false, "abs": false, "hand_brake": false, "seat_belt": true
  },
  "trip": {
    "distance_km": 12.4, "fuel_used_l": 1.03, "avg_lph": 8.3,
    "avg_speed_kmh": 44.0, "range_km": 380, "seconds": 1010
  },
  "odometer_km": 214300.5,
  "gps": { "valid": true, "lat": 56.4845, "lon": 60.2521, "course_deg": 41.5, "speed_kmh": 63 },
  "device": { "alive": true, "firmware": "1.3", "uptime_s": 5840, "restarts": 0, "bus_errors": 0 }
}
```

**Устаревание:** если `connected = false` дольше 1.5 с — `data_valid = false`,
числа остаются последними, но клиент обязан их не показывать как живые.

### 4.2 `GET /api/v1/climate` — состояние климата

```json
{
  "ok": true, "ts": 1794012345678, "valid": true, "age_ms": 120,
  "ac": true, "auto": false, "recirculation": false,
  "defrost_front": false, "fan_auto": false,
  "setpoint_c": 22.5, "fan_level": 3, "airflow": "face",
  "cabin_temp_c": 24.0, "evaporator_temp_c": 6, "setpoint_right_c": 22.0
}
```

- `valid = false` — кадр `0x510` давно не приходил; остальные поля `null`.
- `airflow`: `face` | `feet` | `face_feet` | `auto` | `null`.
- `fan_level`: 0…7, `-1` — неизвестно.

### 4.3 `POST /api/v1/climate/command` — нажать кнопку климата

Тело:

```json
{ "action": "temp_up", "hold_ms": 100 }
```

Допустимые `action`: `temp_up`, `temp_down`, `fan_up`, `fan_down`, `auto`,
`ac`, `recirculation`, `defrost_front`, `defrost_rear`, `mode_face`,
`mode_feet`, `mode_face_feet`, `temp_up_right`, `temp_down_right`.
`hold_ms` необязателен (по умолчанию 100, допустимо 50…1000).

Ответ **сразу**, без ожидания панели:

```json
{ "ok": true, "id": 42 }
```

Коды ответа: `202` — принято; `409` — уже выполняется другая команда;
`400` — неизвестное действие или параметр; `503` — нет связи с шиной.

**Почему не блокируемся:** нажатие панели занимает до 700 мс (CAN-ответ
`0x541`). Держать HTTP-запрос открытым значит ради простоты клиента
блокировать сервер. Поэтому команда возвращает `id`, а результат приходит
событием в WebSocket (§6.3) или запросом §4.4 — кто как хочет.

### 4.4 `GET /api/v1/climate/result/{id}` — чем кончилась команда

```json
{ "ok": true, "id": 42, "action": "temp_up", "state": "done" }
```

`state`: `pending` | `accepted` | `done` | `no_change` | `busy` |
`unknown_action` | `no_panel` | `timeout` | `not_sent`.
Хранится последние 32 команды, старые вытесняются.

### 4.5 `GET /api/v1/health` — жив ли узел

```json
{ "ok": true, "role": "dashboard", "version": "1.0", "uptime_s": 5840,
  "can": { "interface": "can0", "connected": true, "frames": 1234567 } }
```

Используется для проверки кабеля и для «маячка» в приложении Android.

## 5. HTTP: медиа (`10.0.0.2:8080`)

Приборка **спрашивает** у мультимедиа, что играет (уже реализовано в
`MediaBackend`, формат не меняем — только фиксируем):

```json
{ "title": "Song", "artist": "Artist", "station": "",
  "source": "fm", "playing": true, "position": 42, "duration": 213,
  "art": "http://10.0.0.2:8080/art/123.jpg" }
```

- `source`: `fm` | `bt` | `usb` | `stream`.
- `position`/`duration` — секунды; `duration = 0` — неизвестно (радио).
- нет ответа 3 раза подряд — `MediaBackend.available = false`.

---

## 6. WebSocket: `ws://10.0.0.1:8080/ws`

Одно соединение, сообщения — JSON-объекты с полем `type`. Неизвестные типы
игнорируются. Клиент обязан подключаться заново при обрыве (пауза 1 с,
таймаут 5 с, максимум — без ограничения).

### 6.1 Приборка → мультимедиа

**Событие ввода** (джойстик, по правилу фокуса):

```json
{ "type": "input", "code": "nav", "state": "press", "ts": 1794012345678 }
```

`code`: `menu`, `back`, `option`, `radio`, `media`, `nav`, `tel`, `up`,
`down`, `left`, `right`, `press`, `next`, `prev`.
`state`: `press` (сейчас всегда `press`; `release` появится, если нужны
длительные нажатия — клиент должен быть к нему готов).

**Снимок телеметрии** раз в секунду (то же, что `GET /api/v1/car`, но
пушить дешевле, чем опрашивать):

```json
{ "type": "car", "data": { … тот же объект, что §4.1 … } }
```

**Статус узла** раз в 5 с: `{"type":"status","can":true,"uptime_s":5840}`.

### 6.2 Мультимедиа → приборка

**Навигация** — при движении по маршруту, **1 раз в секунду**:

```json
{
  "type": "nav", "active": true, "ts": 1794012345678,
  "maneuver": "left", "distance_m": 240, "street": "ул. Ленина",
  "speed_limit_kmh": 60, "eta_s": 900, "remaining_m": 12400
}
```

- `maneuver`: `straight` | `slight_left` | `left` | `sharp_left` |
  `slight_right` | `right` | `sharp_right` | `uturn` | `roundabout` |
  `arrive` | `none`.
- `active = false` — маршрута нет; приборка гасит блок подсказок.
- `source` (необязательно): `yandex_maps` | `dgis` | `osm` | `other` — откуда
  пришли подсказки. Приборке это нужно только для диагностики и подписи,
  но когда подсказки парсятся из уведомлений третьего приложения, знать
  источник полезно: меняется формулировка — сразу видно, чья.
- **Устаревание:** нет сообщений 3 с → приборка считает навигацию
  потерянной и убирает подсказки (не показывает «поверните через 240 м»,
  когда неизвестно где машина).

**Готовность клиента:**

```json
{ "type": "hello", "role": "media", "version": "1.0", "api": 1 }
```

Из него приборка понимает, что Android жив, и начинает пересылать `input`.

**Подписка на кадры карты:**

```json
{ "type": "map_subscribe", "on": true, "max_width": 1920, "max_height": 720,
  "fps": 1, "quality": 70 }
```

Приборка просит кадры, когда вошла в навигационный режим и активен маршрут.
Кадры идут, только пока подписка включена: в обычном режиме приборка их не
хочет, и канал не должен тратиться на картинку, которую никто не смотрит.

**Результат команды климата:**

```json
{ "type": "climate_result", "id": 42, "action": "temp_up", "state": "done" }
```

### 6.4 Кадры карты (двоичные сообщения)

Android раз в секунду присылает **снимок своего навигационного экрана**, а
приборка показывает его в навигационном режиме — за приборами, уехавшими в
углы. Так карта остаётся полноценной (её рисует Android), а приборке не нужны
ни тайлы, ни маршрутный движок.

**Формат кадра** (WebSocket, binary):

| Смещение | Размер | Что |
|---|---|---|
| 0 | 2 | сигнатура `M` `F` (0x4D, 0x46) |
| 2 | 1 | версия формата: `1` |
| 3 | 1 | формат изображения: `1` = JPEG |
| 4 | 2 | ширина, uint16 big-endian |
| 6 | 2 | высота, uint16 big-endian |
| 8 | 4 | время кадра, секунды epoch, uint32 |
| 12 | … | данные JPEG |

Пример минимальной реализации на Android: `Bitmap.compress(JPEG, quality)` и
отправка заголовка + массива байт.

**Правила:**

- кадры шлются **только по подписке** (`map_subscribe`), не чаще 2 Гц;
- приборка не принимает кадры больше **400 КБ** (переполненный канал хуже,
  чем отсутствие карты) и кадры размером не 1920×720 — масштабирует сама,
  но просит в подписке нужный размер;
- нет кадра 3 с → приборка убирает карту и показывает карточку манёвра
  (вариант без карты), а не «застывший» снимок;
- приборка может запросить `quality` 40–85; по умолчанию 70.

**Почему снимок, а не поток:** поток видео — это кодек, буферизация и
рассинхрон со звуком, которые нам не нужны. Снимок раз в секунду для карты на
приборке неотличим от видео, весит 100–200 КБ (то есть 0,2 МБ/с по 1 Гбит) и
не требует ни декодера, ни синхронизации.

### 6.5 Возможности клиента (что умеет Android)

При подключении клиент говорит, что он умеет, — и приборка подстраивается:

```json
{ "type": "hello", "role": "media", "version": "1.0", "api": 1,
  "caps": { "nav": true, "map_frames": true, "climate": true } }
```

- `map_frames: true` — Android умеет отдавать снимки карты. **Важно:**
  приложения без права захвата экрана (например, с `FLAG_SECURE`) отдают
  чёрный кадр, поэтому мост на Android должен честно проверять это при
  запуске и присылать `false`, а не мусор;
- `map_frames: false` — приборка никогда не подписывается на кадры и живёт
  с подсказками и карточкой манёвра (вариант без карты).

## 7. Частоты и устаревание

| Поток | Частота | Устаревание |
|---|---|---|
| `car` (WS) | 1 Гц | нет данных 1.5 с → `data_valid=false` на приборке |
| `GET /api/v1/car` | по требованию, ≤10 Гц | — |
| `climate` состояние | по кадру `0x510` = 5 Гц | `age_ms > 1000` → `valid=false` |
| `climate_result` | по событию | таймаут нажатия 700 мс |
| `nav` | 1 Гц при активном маршруте | 3 с → подсказки скрыть |
| `map_frame` | 1 Гц по подписке | 3 с → карту скрыть, показать карточку манёвра |
| `input` | по событию (нажатие) | — |
| медиа (`GET /api/media`) | 1 Гц опрос | 3 промаха → `available=false` |
| `status`, `hello` | 5 с / при подключении | — |

## 8. Ошибки

| HTTP | `error` | Когда |
|---|---|---|
| `400` | `bad_request` | битый JSON, неизвестное действие, `hold_ms` вне 50…1000 |
| `404` | `not_found` | неизвестный путь или `id` команды |
| `409` | `busy` | ещё выполняется предыдущая команда климата |
| `503` | `can_unavailable` | шина не открыта, команда не ушла |
| `504` | `climate_timeout` | ESP32 не ответил (только в `result`, не в POST) |

Тело ошибки: `{ "ok": false, "error": "busy" }`.

---

## 9. Поведение при отказах

| Что пропало | Приборка | Мультимедиа |
|---|---|---|
| Ethernet-кабель | работает как есть; подсказки навигации скрыты, медиа-виджет «нет связи» | работает как есть; не получает `input`, климат недоступен |
| Android перезагружается | ничего не меняется, кроме исчезновения подсказок | при старте ждёт приборку и подключается заново |
| Приборка перезагружается | — | переподключается, повторяет `hello`, `nav` продолжает шлать (без ответа — просто пишет в лог) |
| ESP32 климата нет | `climate.valid=false` | команды возвращают `503`/`no_panel` |

Правило: **ни одна сторона не блокируется ожиданием второй.** Всё, что
зависит от сети, — необязательное улучшение.

## 10. Открытые вопросы

1. **Кто на Android отдаёт медиа-JSON** — отдельное мини-приложение, сервис
   в составе лаунчера, или `Termux`+скрипт на время разработки? Порт 8080.
1a. **Захват экрана навигатора.** Яндекс Навигатор и 2ГИС — закрытые
   приложения: подсказки из них можно получить только из уведомлений, а
   снимок карты — только если они сами не запрещают захват. Проверка до
   покупки железа: включить видеозапись экрана при работающей навигации и
   посмотреть, видна ли карта (чёрный кадр = `FLAG_SECURE`).
2. **Арт обложек** (`art`): отдавать картинку по URL или base64 в JSON
   (при обложках 100–200 КБ base64 по WebSocket — плохая идея).
3. **Время и часовой пояс**: приборка отдаёт UTC в `ts`; ставит ли Android
   своё время сам, или синхронизируется от приборки (в `car` можно добавить
   `utc_hms`)?
4. **Камера заднего хода** — на приборку, на Android или на оба? Если на
   приборку, нужен ещё поток (пока не проектируем).
5. **Прошивка Android для `hello`**: если клиент старый и не шлёт `hello`,
   приборка считает, что Android не готов, и не пересылает `input` —
   это надо помнить при обновлении одной стороны.
