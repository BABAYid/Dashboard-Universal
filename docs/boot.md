# Быстрый запуск приборки: как измерить и что чинить

Задача: от появления ACC до живых приборов на экране — как можно меньше
времени. Поставщик 022A присылает образ Debian; на нём всё и делается.

**Главное, что нужно знать заранее:** на RK3588 с вендорским Debian время
загрузки на 70–90 % состоит из userspace (systemd, службы, инициализация оконной
системы) и запуска Qt-приложения. Ядро — оставшиеся 10–30 %. Собирать своё
ядро в первую очередь — самая трудоёмкая и самая малополезная часть работы.
Правильный порядок: измерить → выключить лишние службы → ускорить приложение →
и только потом ядро.

---

## 0. Сначала цифра

Без честного замера всё остальное — гадание. Три отметки, которые нужны:

1. **ACC подан** — единственная отметка, которая находится вне платы. Её даёт
   супервизор питания (см. ARCHITECTURE.md): он по оптрону видит ACC и пишет
   время в журнал. Без него любой замер начинается с «ядра», а водителя
   интересует «от ключа».
2. **Первый кадр приборки** — уже есть в проекте: `main.cpp` ловит
   `afterRendering` и ставит `firstFrameRendered`, а QML пишет в лог.
3. **Приборы проявились** — конец нашей стартовой заставки.

На плате замеры:

```bash
systemd-analyze                    # firmware / loader / kernel / userspace
systemd-analyze blame | head -30   # кто сколько съел в userspace
systemd-analyze critical-chain     # что ждёт чего
systemd-analyze plot > boot.svg    # картинка, удобно смотреть глазами
cat /proc/cmdline                  # параметры ядра
dmesg | head -40                   # момент старта ядра и инициализация
```

Скрипт-помощник (запускать после загрузки, складывает всё в один файл):

```bash
tools/boot-report.sh > ~/boot-before.txt
```

## 1. Userspace: самый большой выигрыш за самый короткий срок

Вендорский Debian — это универсальная система: в ней Bluetooth, печать,
модемы, snaps, обновления по таймеру, иногда полный графический стол. Нам
нужны: ядро, сеть (позже), наш `appDashboard`, и одна служба для него.

Что смотреть и что выключать (проверять по одному, после каждого — повторный
`systemd-analyze blame`):

```bash
systemctl list-unit-files --state=enabled
```

Типичные кандидаты (у нас они точно не нужны):

- `bluetooth`, `cups*`, `avahi-daemon`, `ModemManager`, `NetworkManager-wait-online`,
- `snapd*`, `unattended-upgrades`, `apt-daily*`, `man-db`, `fwupd`,
- `rpcbind`, `nfs-*`, `samba*`, `smbd`, `getty@tty*` (кроме одного) — если
  консоль нужна только для наладки;
- графический вход: `lightdm`/`gdm`/`sddm` и `display-manager` — приборка
  запускается прямо из systemd на EGLFS, без X/Wayland и без рабочего стола.

**Не ждать сеть.** Наше приложение не должно зависеть от `network-online.target`:
сеть — улучшение (карта, медиа), а приборы работают без неё. В unit-файле
никакого `After=network-online.target`.

Служба приборки (черновик, лежит в `deploy/systemd/dashboard.service`):

```ini
[Unit]
Description=Audi Dashboard
After=local-fs.target
Wants=local-fs.target

[Service]
Type=simple
ExecStart=/opt/dashboard/appDashboard --can can0
Restart=always
RestartSec=1
Environment=QT_QPA_PLATFORM=eglfs
Environment=QT_LOGGING_RULES=*=false

[Install]
WantedBy=multi-user.target
```

Проверять: `systemd-analyze critical-chain` — наша служба должна висеть на
`local-fs.target`, а не на «сети».

Ещё две вещи:

- **Корневая ФС только для чтения** (или overlayfs): на старте пропадает
  проверка ФС и лишние записи, а при внезапном снятии питания ничего не
  бьётся. Приборка ничего не пишет, кроме настроек — их можно держать в
  tmpfs и сохранять редко.
- **Командная строка ядра**: `quiet loglevel=3` (меньше вывода — меньше
  времени на консоль), убрать лишние `console=`.

Ожидаемый выигрыш от этого этапа на вендорском образе: **от 5 до 20 секунд.**

## 2. Приложение: что уже сделано и что добавить

В проекте уже учтено:

- QML собирается в байткод на этапе сборки (`qt_add_qml_module` + qmlcachegen
  в Release), а не парсится при старте;
- карта (`QtWebEngine`) не поднимается, пока не войдёшь в навигацию;
- шрифт лежит в ресурсах, а не ищется по системе;
- первый кадр ловится явно (`afterRendering`), а стартовая анимация ждёт его.

Что стоит сделать для производства:

1. **3D-модель грузить ПОСЛЕ первого кадра.** `RuntimeLoader` разбирает
   glb (17 узлов, 2 МБ) в потоке рендера — на старте это заметная пауза.
   Гаужи должны появиться раньше, чем машина.
2. **Отключить логирование в релизе**: `QT_LOGGING_RULES=*=false` и убрать
   `console.log` из горячих мест (у нас их немного).
3. **Стартовая заставка — вопрос решения.** Сейчас сборка машины занимает
   ~5.4 с и настраивалась «на глаз» под красоту, а приборы проявляются в
   конце. Для производства логичнее: приборы сразу, а сборка машины — фоном
   в центральной зоне. Это не «ускорение», а перенос ощущения времени.
4. **Кэш шейдеров RHI** (Qt 6.6+): сохранять на диск после первого запуска,
   чтобы не компилировать программные шейдеры каждый раз.
5. Мелочи: `-O2`/LTO в релизной сборке, отключить `QML_DISK_CACHE` в
   непрогретом виде, проверить, что не грузятся неиспользуемые плагины.

Ожидаемый выигрыш: **2–5 секунд** до первого осмысленного кадра.

## 3. Ядро: когда userspace уже выжат

Своё ядро на RK3588 собирают **из вендорских исходников**, а не из mainline:
mainline не знает всех блоков 022A (LVDS-панель, GPU-драйвер, питание), и
половина «ускорения» обернётся чёрным экраном.

Как это выглядит на практике:

```bash
# 1. Получить от поставщика исходники: kernel + U-Boot + build.sh (SDK Rockchip)
# 2. Собрать ровно как поставщик — сначала без изменений, чтобы получить эталон
./build.sh kernel
# 3. Только потом править конфиг:
make ARCH=arm64 CROSS_COMPILE=aarch64-linux-gnu- menuconfig
```

Что реально помогает времени загрузки:

- **Сжатие ядра LZ4** вместо gzip (`CONFIG_KERNEL_LZ4`) — распаковка быстрее,
  выигрыш доли секунды, но бесплатно;
- **убрать initramfs**, если он есть: загрузка сразу с корневого раздела
  снимает 0.5–2 с (и лишнюю пересборку при каждом изменении);
- **отключить ненужные драйверы** (камеры, аудиокодеки, USB-гаджеты, чужие
  WiFi/Bluetooth, RAID, шифрование): меньше инициализаций и меньше размер;
- **`initcall_debug`** в cmdline один раз — чтобы увидеть, какие драйверы
  инициализируются дольше всех, и отключить именно их;
- не выключать: LVDS/eDP, GPU (Mali), I2C (тач, если будет), Ethernet, GPIO.

Проверка после каждой сборки — только замером, а не на глаз.

Риск: любая правка конфига может отвалиться на железе (экран, тач, сеть).
Поэтому этап 3 делается **когда этапы 1–2 уже дали результат** и есть
рабочий образ для отката.

Ожидаемый выигрыш: **1–3 секунды.**

## 4. U-Boot и device tree

Последние крохи: убрать ожидание USB/сети в загрузчике, сократить
инициализацию лишних интерфейсов, `bootdelay=0`. Обычно это **0.3–1 с**, и
тут легко сломать загрузку — только с JTAG/серийной консолью под рукой.

## 5. Чего ждать в итоге

Ориентиры для вендорского Debian на RK3588 (приборка без рабочего стола):

| Состояние | Время от ACC до приборов |
|---|---|
| как пришло от поставщика | 25–45 с |
| после этапа 1 (службы) | 12–20 с |
| после этапа 2 (приложение) | 8–13 с |
| + своё ядро (этап 3) | 6–10 с |
| + U-Boot/DT (этап 4) | 5–9 с |

Пять секунд «как в машинах» на вендорском BSP почти недостижимы: часть
времени тратит аппаратная инициализация DDR и загрузчик. Честная цель —
**8–10 секунд до приборов и ~3 секунды до первого кадра** (экран уже не
чёрный, идёт заставка).

## 5.1 Где собирать: решено 6.11.2026

**Полная сборка ядра — на самой плате 022A.** Причины:

- у RK3588 восемь ядер и пассивный радиатор, рассчитанный на непрерывную
  работу; полная сборка там идёт 25–40 минут;
- у рабочего ноутбука (HP Pavilion, AMD A10-8700P, 12 ГБ DDR3) 63 °C уже на
  простое, был случай перегрева при сборке, после которого погиб модуль
  памяти. Гонять на нём многочасовые сборки — риск железу без выигрыша.

На ноутбуке остаётся то, что не греет:

| Задача | Где |
|---|---|
| Правка device tree, `make dtbs` (секунды) | ноутбук |
| Сборка приложения Qt | ноутбук (кросс) или плата — по факту |
| Полная сборка ядра и модулей | **плата** |
| Сборка образа вендорским `build.sh` | ноутбук, один раз (Docker на x86_64) |

Если всё же понадобится собирать ядро на ноутбуке: `-j2`, `ccache`,
`watch -n2 sensors` рядом, при 80 °C — остановить. Свободной памяти 12 ГБ
для сборки ядра хватает с запасом (пик 2–3 ГБ): ограничение там тепловое,
а не по объёму.

## 6. Что попросить у поставщика сразу

1. Исходники: `kernel`, `u-boot`, `build.sh`, конфиги defconfig.
2. Команду, которой они собирают образ (иначе не воспроизвести).
3. Командную строку ядра из их образа (`/proc/cmdline` на живой плате).
4. Есть ли initramfs и зачем.
5. Точные параметры панели в device tree (LVDS-тайминги) — чтобы не
   потерять картинку, если будем править DT.

## 7. Порядок работ для нас

- [ ] Получить образ и исходники, загрузиться, снять `boot-report.sh`.
- [ ] Отключить службы, поставить `dashboard.service`, проверить ACC→кадры.
- [ ] Догрузить 3D-модель после первого кадра, отключить логи в релизе.
- [ ] Пересобрать ядро из вендорских исходников: LZ4, без initramfs,
      без ненужных драйверов.
- [ ] Ручки U-Boot/DT только если после этого останется что резать.
