# Android-мост: приложение на мультимедиа

Спека приложения, без которого приборка и мультимедиа не разговаривают.
Контракт сети — `docs/integration.md`; здесь — что именно делает Android.

Пока приложения нет, его роль в отладке играет `tools/nav_test_client.py`.

---

## 1. Зачем оно нужно

Приборка умеет принимать подсказки и кадры карты, но сама их взять не может:
навигация живёт в закрытых Яндекс Навигаторе и 2ГИС, у которых нет API. Мост
делает ровно три вещи, которые Android позволяет делать штатно:

1. **читает уведомление навигатора** (`NotificationListenerService`) —
   оттуда берутся знак манёвра и расстояние;
2. **снимает экран** (`MediaProjection`) — из этого получается кадр карты;
3. **читает медиа-сессию** (`MediaSessionManager`, работает с тем же
   разрешением на уведомления) — из этого получается «что играет».

Плюс мост — клиент WebSocket: получает от приборки события джойстика и
данные машины, отдаёт подсказки, кадры и свои `hello`.

---

## 2. Что делает и чего не делает

| Делает | Не делает |
|---|---|
| Читает уведомления навигатора, превращает в `nav` | Не строит маршруты и не рисует карту сам |
| Снимает экран и шлёт кадры по подписке | Не хранит карты и не качает тайлы |
| Отдаёт медиа-JSON по HTTP | Не управляет климатом напрямую — только через HTTP приборки |
| Ловит `input` от приборки | Не занимается CAN и железом машины |
| Показывает статус связи (если включить) | Не является навигатором и не заменяет Яндекс/2ГИС |

## 3. Компоненты

| Компонент | Android API | Что делает |
|---|---|---|
| `BridgeService` (foreground) | `Service` + `startForeground` | держит WS, таймеры, жизненный цикл |
| `NotificationWatcher` | `NotificationListenerService` | парсит навигационные уведомления |
| `ScreenCapturer` | `MediaProjection` + `ImageReader` | кадры экрана в JPEG |
| `MediaWatcher` | `MediaSessionManager` | метаданные текущей сессии |
| `MediaHttpServer` | `ServerSocket` (или Ktor/NanoHTTPD) | `GET /api/media` на :8080 |
| `InputRouter` | `AccessibilityService` (по желанию) | глобальные BACK/HOME для событий джойстика |
| `MockLocationFeeder` | `LocationManager.addTestProvider` | координаты с приборки в систему |
| `UiLauncher` (наш) | обычная Activity | интерфейс мультимедиа, климат, навигация — рисует дизайнер |

Все компоненты живут в одном приложении: отдельные приложения обменивались бы
разрешениями через сложные схемы, а нам нужно, чтобы это пережило перезагрузку
и работало без участия пользователя.

---

## 4. Разрешения и настройки, которые придётся выдать один раз

| Что | Зачем | Как выдаётся |
|---|---|---|
| «Доступ к уведомлениям» | читать уведомления навигатора и медиа-сессию | Настройки → Спец. доступ → Уведомления |
| «Запись экрана» (MediaProjection) | кадры карты | диалог каждый запуск; можно запомнить намерение через `MediaProjectionManager` + сохранённый токен (Android 14+ — только один раз за загрузку) |
| «Приложение для фиктивных местоположений» | отдавать координаты с приборки | Настройки разработчика → Выбор приложения для фиктивных местоположений |
| Спец. доступ «Служба доступности» | глобальные BACK/HOME с джойстика | Настройки → Спец. доступ → Службы доступности (по желанию) |
| Уведомления (постоянное) | foreground-сервис | первый запуск |

**Важный момент про Android 14+:** `MediaProjection` требует согласия
пользователя на каждую сессию, а токен одноразовый. Поэтому при старте моста
диалог может появляться. Обходной путь для автомобиля: экран мультимедиа —
наш лаунчер, и диалог показывается один раз при включении, а сервис создаёт
`VirtualDisplay` и больше не останавливает его. Если согласие не дано —
мост честно сообщает приборке `caps.map_frames: false`, и приборка живёт с
карточкой манёвра.

## 5. Подсказки навигации: разбор уведомлений

Источник — уведомление, которое показывают Яндекс Навигатор и 2ГИС, пока
маршрут активен. Формулировки бывают разные, поэтому парсер разбирает только
то, что устойчиво:

1. берём цифры + единицы: `200 м`, `1,2 км`, `150 метров`;
2. ищем ключевое слово манёвра: «поверните налево», «направо», «возьмите
   правее», «держитесь левее», «разворот», «двигайтесь прямо», «прибыли»,
   «круговое движение»;
3. извлекаем название улицы после «на …» — если получается.

Таблица манёвров (та же, что в контракте):

| Текст в уведомлении | `maneuver` |
|---|---|
| «прямо», «через … м прямо» | `straight` |
| «левее», «плавно влево» | `slight_left` |
| «налево» | `left` |
| «резко налево» | `sharp_left` |
| «правее» | `slight_right` |
| «направо» | `right` |
| «резко направо» | `sharp_right` |
| «разворот» | `uturn` |
| «круговое», «съезд … » | `roundabout` |
| «прибыли», «финиш» | `arrive` |

Правила:

- раз в секунду собираем `nav`-сообщение и шлём, даже если текст не изменился:
  приборка считает данные устаревшими через 3 с (иначе расстояние
  «застывает»);
- уведомление исчезло (маршрут закрыт) → `{"type":"nav","active":false}`;
- текст не распознан → шлём только то, что поняли (`maneuver: "none"`,
  `distance_m` из цифр, если нашли); ничего не поняли — не шлём вообще, чтобы
  не затирать последнюю нормальную подсказку мусором;
- **название пакета** навигатора отдаём в `source`: `yandex_maps`,
  `dgis`, иначе `unknown`. Так приборка сможет показывать, откуда подсказка,
  и мы увидим в логах, откуда пришёл текст.

Парсер пишется отдельным классом с unit-тестами на строках-образцах — это
единственное место в проекте, где текст зависит от чужого приложения, и его
надо покрыть тестами сразу.

## 6. Кадры карты

- `map_subscribe {on:true}` приходит только когда приборка в навигации;
- создаём `VirtualDisplay` на размер `min(экран, max_width/max_height)`;
- раз в секунду `ImageReader` → `Bitmap` → `JPEG quality` из подписки
  (по умолчанию 70) → заголовок из контракта → бинарный кадр WS;
- если приложение навигатора запрещает захват (`FLAG_SECURE`) — в кадре
  будет чёрный прямоугольник. Проверяем при старте один раз: снимаем кадр,
  смотрим, что он не однотонный; если однотонный — `caps.map_frames: false`
  и больше не тратим ресурсы;
- подписка выключена — `VirtualDisplay` освобождаем (он ест батарею и GPU);
- давление по памяти: JPEG 1920×720 обычно 100–200 КБ, это норма; кадры
  больше 400 КБ мост не отправляет (сам уменьшает quality).

## 7. Медиа-JSON

`GET http://<android>:8080/api/media` → объект по контракту §5:

```json
{ "title": "…", "artist": "…", "station": "", "source": "fm",
  "playing": true, "position": 42, "duration": 213, "art": "" }
```

Источник — `MediaSessionManager.getActiveSessions()`: берём сессию с
воспроизведением, читаем `MediaMetadata` (`TITLE`, `ARTIST`) и
`PlaybackState` (`position`, `speed`). `source` определяем по пакету
(`fm` для радио, `usb` для плеера и т. д.), `duration` = 0 для радио.
`art` — URL обложки, если найдётся локальный кэш; иначе пусто (приборка не
обязана показывать обложки).

## 8. Климат и джойстик

- **Климат** рисуется нашим интерфейсом на Android. Любое нажатие →
  `POST /api/v1/climate/command` на приборку; состояние → `GET /api/v1/climate`
  (раз в секунду) или из `car`. Никаких прямых пакетов на ESP32: один путь,
  одно место правды.
- **Джойстик**: WS-клиент получает `{"type":"input","code":"left"}`.
  - в нашем лаунчере/климате/списках — двигаем фокус, нажатие = выбор,
    энкодер = изменение значения;
  - в чужих приложениях (Яндекс, 2ГИС) — только глобальные действия:
    BACK закрывает панель, HOME выходит (через `AccessibilityService`,
    если пользователь его включил).

Это ограничение честное: чужие приложения не рассчитаны на D-pad, и
пытаться эмулировать касания по координатам — путь к непредсказуемому
поведению. Джойстик работает там, где интерфейс наш, а в навигаторе
управление — пальцем.

## 9. Координаты для навигатора

Яндекс/2ГИС спрашивают систему `LocationManager`, а у 022A своего приёмника
нет. Поэтому мост подменяет местоположение:

1. в настройках разработчика пользователь выбирает мост как
   «приложение для фиктивных местоположений» (один раз);
2. мост создаёт тестовый провайдер `bridge_gps` и раз в 100 мс кормит его
   координатами с приборки (из `car.gps` по WS, 10 Гц);
3. навигатор получает обычные `Location`-обновления и не знает, что они не
   с системного приёмника.

Если mock location окажется неудобным — альтернатива: NEO-M8N по UART прямо
к мультимедиа (тогда координаты уже системные). Это решение принимается
после первых опытов на живой плате.

## 10. Жизненный цикл и отказы

| Событие | Поведение |
|---|---|
| Загрузка Android | `BOOT_COMPLETED` → старт `BridgeService`, восстановление MediaProjection-токена (если он ещё жив), пауза 2 с, подключение к приборке |
| Нет приборки | повтор каждые 2 с; в UI — «нет связи»; подсказки и кадры копить не нужно |
| Приборка перезагрузилась | WS закрылся → переподключение, повторный `hello` |
| Приборка ушла из навигации | пришёл `map_subscribe {on:false}` → стоп захвата |
| Пользователь отозвал запись экрана | ловим `MediaProjection.Callback.onStop` → `caps.map_frames:false` при следующем `hello` |
| Навигатор закрыт | уведомление исчезло → `nav {active:false}` |
| Парсер не понял текст | ничего не шлём (см. §5) |
| Сервис убит системой | `START_STICKY` + foreground, чтобы не убивали |

## 11. Отладка

- Тег логов `bridge`: `adb logcat -s bridge`.
- Диагностический экран в приложении (для отладки на столе): состояние WS,
  последнее `nav`, размер последнего кадра, откуда пришёл текст уведомления,
  выбор пакета навигатора.
- **Режим «без телефона»**: приложение умеет слать синтетические подсказки
  (как `tools/nav_test_client.py`), чтобы можно было проверить связку, не
  запуская навигатор.
- Проверка контракта с ПК: `curl http://<android>/api/media`,
  `websocat ws://<приборка>:8080/ws`.

---

## 12. Порядок работ

1. **Парсер уведомлений** + тесты на строках-образцах (можно сделать на
   телефоне, без машины).
2. **Медиа-сервер** и медиа-сессия (проверяется `curl`-ом).
3. **WS-клиент** по контракту (`hello`, `nav`, `input`, `map_subscribe`).
4. **Захват экрана** и кадры.
5. **UI лаунчера** (климат, медиа, навигация) — параллельно с дизайнером.
6. **Mock location** и первый запуск Яндекс Навигатора с приборкой.
