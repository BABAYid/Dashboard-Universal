# Прошивка модуля ввода: джойстик BMW iDrive (ESP32)

Модуль ввода берёт джойстик BMW iDrive (F20/F30) и превращает его нажатия и
повороты в кадр `0x530` «СОБЫТИЕ ВВОДА» для приборки. Протокол шины —
`can_protocol_v1.4.txt` в корне проекта, версия прошивки — 1.0.

Это отдельная прошивка и отдельная ESP32: блок сбора (`firmware/`) провода
машины читает, а модуль ввода — только джойстик. Общего у них ничего, кроме
шины и протокола, поэтому проект собран отдельно:

```
   джойстик BMW F20
   (кнопки, энкодер,
    подсветка)
          │  CAN 500 кбит/с, 11-бит ID
          │  0x267/0x264 ← от него, 0x563/0x273/0x202 → ему
          ▼
   ┌──────────────────┐        0x530 (события ввода)        ┌──────────┐
   │ ESP32 модуля     │ ──────────────────────────────────► │ приборка │
   │ ввода (эта       │                                     │ RK3588   │
   │ прошивка)        │ ◄────── 0x200 (габариты) ────────── │          │
   └──────────────────┘                                     └──────────┘
                            ▲ 0x100…0x7F0 (данные машины)
                            │
                      блок сбора (firmware/)
```

## Что делает прошивка

* держит джойстик «живым»: heartbeat `0x563` каждые 100 мс и «пробуждение»
  `0x273` при старте, а также после 2 секунд тишины от джойстика;
* разбирает события джойстика `0x267` (кнопки MENU/BACK/OPTION/RADIO/MEDIA/
  NAV/TEL, направления, нажатие на ручку) и `0x264` (энкодер);
* отправляет на приборку кадр `0x530` на каждое событие — и на нажатие, и на
  отпускание, и на каждый поворот энкодера со знаковой дельтой;
* включает подсветку кнопок (`0x202 FD`, два кадра подряд) по фронту
  «габариты включились» из кадра блока сбора `0x200` (байт 0, бит 4);
* следит за состоянием шины и поднимает её после bus-off;
* раз в 5 секунд печатает в консоль счётчики принятых/отправленных кадров и
  состояние шины.

Чего прошивка НЕ делает (осознанно):

* не читает провода машины — это блок сбора, у него свой кадр `0x200`;
* не обрабатывает `0x5E7` (подтверждение событий джойстика) — иначе приборка
  получала бы по два кадра `0x530` на каждое нажатие;
* не уходит в сон по зажиганию: джойстик запитан от того же провода, что и
  ESP32, а модуль без heartbeat всё равно засыпает сам. См. «Грабли».

## Распиновка

Пины взяты из проекта селектора АКПП (`PlatformIO/Projects/AKPP_Selector`):
там джойстик BMW уже работал на этой паре выводов.

| Что | Вывод ESP32 | Куда |
|---|---|---|
| CAN TX | GPIO5 | `CTX` трансивера (SN65HVD230, вывод 1 = `D`) |
| CAN RX | GPIO4 | `CRX` трансивера (вывод 4 = `R`) |
| Питание трансивера | 3V3 | `VCC` (трансивер строго 3.3 В — 5 В сожжёт входы ESP32) |
| Земля | GND | `GND` трансивера **и** джойстика |
| CAN H / CAN L | — | `CANH`/`CANL` трансивера → шина, вместе с блоком сбора и приборкой |

Требования к шине:

* скорость **500 кбит/с**, стандартные 11-битные ID, 8 байт данных;
* согласующие резисторы 120 Ом **на двух концах** шины (в трансивере модуля и
  у приборки); больше двух терминаторов на шину не ставить;
* общая земля у всех узлов — иначе контроллер TWAI набирает ошибки и уходит
  в bus-off, хотя «провод вроде подключён».

## Кадры на шине

### От нас джойстику

| ID | Данные | Когда |
|---|---|---|
| `0x202` | `FD` | подсветка кнопок; **два кадра подряд** — одиночный модуль игнорирует. Только по фронту «габариты включились» |
| `0x563` | `63` | heartbeat, каждые **100 мс**, постоянно, независимо от нажатий |
| `0x273` | `1D E1 00 F0 FF 7F DE 00` | «проснись»: при старте и повторно, если от джойстика 2 с нет ни `0x267`, ни `0x264` |

### От джойстика нам

`0x267` — события, формат `E1 FD [счётчик] [состояние] [модификатор] [указатель]`:

| Модификатор (байт 4) | Что это | Состояние (байт 3) | Указатель (байт 5) |
|---|---|---|---|
| `C0` | кнопка | `00` отпущена / `01` нажата | `01` MENU, `02` BACK, `04` OPTION, `08` RADIO, `10` MEDIA, `20` NAV, `40` TEL |
| `DD` | направление | `11` вперёд, `41` назад, `21` вправо, `81` влево, `00` отпущено | — |
| `DE` | нажатие на ручку | `00` / `01` | `01` |

`0x264` — энкодер, формат `E1 FD [счётчик] [младший байт] [старший байт] 1E`:
байты 3–4 — 16-битный счётчик поворотов. В кадр `0x530` уходит **разность**
с предыдущим значением (знаковая, с учётом переполнения 16 бит), а не сам
счётчик.

`0x5E7` — подтверждение событий, игнорируется.

### От нас приборке: `0x530`

| Байт | Значение |
|---|---|
| 0 | вид события: `01` кнопка, `02` энкодер |
| 1 | код кнопки: `01` MENU, `02` BACK, `03` OPTION, `04` RADIO, `05` MEDIA, `06` NAV, `07` TEL, `08` UP, `09` DOWN, `0A` LEFT, `0B` RIGHT, `0C` PRESS; для энкодера `00` |
| 2 | кнопка: `01` нажата / `00` отпущена; энкодер: знаковая дельта int8 |
| 3 | счётчик событий, +1 на каждый кадр, переполняется на 255 |
| 4–7 | `00` |

Пример строки в логе (ровно так она и выглядит в мониторе):

```
I (12345) input: 0x267: кнопка NAV нажата → 0x530 01 06 01 0A
I (12400) input: 0x267: кнопка NAV отпущена → 0x530 01 06 00 0B
I (13100) input: 0x264: энкодер +2 → 0x530 02 00 02 0C
```

## Сборка и прошивка

Нужен ESP-IDF 5.5 (в рабочей папке проекта лежит готовое окружение в
`.dsh-idf`). Цель — `esp32`.

```bash
cd "/home/oleg/Документы/новая приборка/firmware/joystick"
. /home/oleg/Документы/новая приборка/.dsh-idf/esp-idf-v5.5.6/export.sh   # или свой export.sh
idf.py set-target esp32 build
```

Прошивка (модуль подключён по USB, порт `/dev/ttyUSB0` — подставить свой):

```bash
idf.py -p /dev/ttyUSB0 flash monitor
```

Выйти из монитора — `Ctrl+]`. Стереть настройки в флеше (если модуль ведёт
себя странно после смены версии) — `idf.py -p /dev/ttyUSB0 erase-flash`, потом
`flash`.

Чистая сборка без экспорта окружения (если `export.sh` не подхватился):

```bash
cd "/home/oleg/Документы/новая приборка/firmware/joystick"
IDF_PATH="/home/oleg/Документы/новая приборка/.dsh-idf/esp-idf-v5.5.6" \
IDF_TOOLS_PATH="/home/oleg/Документы/новая приборка/.dsh-idf/tools" \
/home/oleg/Документы/новая приборка/.dsh-idf/esp-idf-v5.5.6/tools/idf.py build
```

## Как проверить

### 1. Стол, без машины и без приборки

Подключить только ESP32 + трансивер + джойстик (12 В на джойстик, земля общая,
терминатор 120 Ом между CAN H и CAN L). В мониторе должно быть:

```
I (312) input: === Модуль ввода: джойстик BMW iDrive (F20/F30) ===
I (312) input: прошивка 1.0, протокол приборки 1.4, кадр событий 0x530
I (322) input: CAN: 500 кбит/с, 11-бит ID, 8 байт, TX=GPIO5, RX=GPIO4
I (332) can: CAN поднят: 500 кбит/с, 11-бит ID, 8 байт, TX=GPIO5, RX=GPIO4
I (332) joy: отправляю джойстику пробуждение (0x273)
```

Нажать кнопки и покрутить энкодер — на каждое событие должна появляться строка
вида `0x267: кнопка MEDIA нажата → 0x530 01 05 01 XX` и через 5 секунд строка
со счётчиками:

```
I (5312) input: шина работает | отправлено 158, принято 3, потеряно 0, ошибок шины 0 | событий 3
```

Признак того, что джойстик не «ожил»: `W joy: от джойстика нет кадров 2000 мс
— повторяю 0x273`. Тогда проверять по порядку: питание джойстика (он питается
не от ESP32!), общую землю, CAN H/L местами не перепутаны, скорость 500 кбит/с.

На столе без второго узла на шине возможен `W can: шина ушла в bus-off` — это
нормально: кадры никто не подтверждает. Шина поднимается сама, повторяющиеся
такие строки означают обрыв или отсутствие терминатора.

### 2. На шине с приборкой

На приборке (RK3588) слушать шину:

```bash
candump can0,530:7FF
```

и жать кнопки джойстика — кадры `530 [8] 01 06 01 XX 00 00 00 00` должны
появляться по одному на каждое нажатие и отпускание, а `530 [8] 02 00 <дельта>
XX …` — на каждый поворот энкодера (по часовой стрелке дельта положительная,
если нет — см. `JOY_ENCODER_INVERT` в `main/config.h`).

Проверка подсветки: включить габариты (блок сбора начнёт слать `0x200` с
битом 4 в байте 0) — в логе модуля появится одна строка
`0x200: габариты включились → 0x202 FD (подсветка, два кадра)`, кнопки
подсветятся. Повторных строк быть не должно: подсветка отправляется только по
фронту. Выключить габариты — модуль ничего не отправляет, подсветка гаснет
сама по своему протоколу.

### 3. Проверка кадра глазами

Любой CAN-адаптер (`can0` на приборке или USB-CAN на компьютере) в режиме
сниффера: на нажатие MENU должно быть ровно два кадра `0x530` (нажата,
отпущена) со счётчиками, отличающимися на 1. Если счётчик прыгает больше чем
на 1 — кадры теряются на шине (проверить терминаторы и длину проводов).

## Грабли и ограничения

* **Джойстик питается отдельно.** ESP32 даёт только CAN-сигнал; 12 В на модуль
  подаётся своим проводом, земля — общая. Без питания джойстик молчит, и это
  выглядит как «нет кадров `0x267`».
* **Подсветка — только по фронту.** Постоянный поток `0x202` модуль
  воспринимает как команду и держит подсветку, но это лишний трафик и риск, что
  выключение габаритов не сработает. Поэтому на выключение не отправляем
  ничего.
* **Повтор `0x273` идёт всё время тишины.** По шине нельзя отличить «джойстик
  спит» от «джойстик не трогают»: пока от него нет кадров, пробуждение уходит
  каждые 2 секунды. Это ~0.5 кадра в секунду, на шине незаметно.
* **Отпускание направления.** В кадре отпускания состояния `0x00` не видно,
  какое направление отпустили, поэтому запоминается последнее нажатое. Если
  джойстик когда-нибудь начнёт присылать отпускание одного направления во
  время нажатия другого, отпускание уйдёт не тому коду.
* **Скачки энкодера.** Дельта в `0x530` — int8, поэтому скачок больше ±127 за
  один кадр ограничивается до ±127 с предупреждением в лог (такое значение —
  признак сбоя на шине, а не поворота).
* **Нет сна по зажиганию.** Модуль работает, пока есть питание: джойстик без
  heartbeat всё равно засыпает сам, а ESP32 в глубокий сон по ACC не уходит —
  сигнала зажигания на этой плате нет. Если понадобится, проще запитать модуль
  от ACC.
* **Счётчик в `0x264` и `0x267` не проверяется.** Потеря кадра на шине не
  ловится: дельта энкодера при потере кадра просто станет больше (и это
  правильная суммарная дельта), а потерянное нажатие восстанавливать нечем.
  Приёмник приборки видит потерю по счётчику байта 3 кадра `0x530`.
