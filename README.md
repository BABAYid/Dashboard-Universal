# Приборная панель (Audi Dashboard)

Виртуальная приборная панель для автомобиля: Qt6/QML-интерфейс на nanoPC-T6 (RK3588),
данные приходят по CAN от блока сбора на ESP32.

```
ESP32 (сбор сигналов)  ──CAN 500 кбит/с──►  nanoPC-T6 (SocketCAN)  ──►  Qt6/QML приборка
```

## Структура

| Путь | Что это |
|---|---|
| `Dashboard/` | Приложение Qt6/QML |
| `Dashboard/Main.qml` | Компоновка макета 1920×720, привязка данных к бэкенду |
| `Dashboard/Speedometer.qml`, `Tachometer.qml` | Приборы (стрелки, шкалы) |
| `Dashboard/Indicators.qml` | Лампы, наружная температура, одометр/trip |
| `Dashboard/Settings.qml` | Окно калибровки коэффициентов |
| `Dashboard/MapWebView.qml` | Карта (OpenStreetMap) в режиме навигации |
| `Dashboard/can/CanBackend.*` | Приём CAN, разбор протокола, демо-режим || `Dashboard/tests/` | Тест разбора протокола |
| `can_protocol_v1.1.txt`, `CAN_protocol_v1.1.odt` | Описание CAN-протокола (версия 1.1) |
| `esp32_wiring.txt` | Таблица подключения сигналов к ESP32 (версия 2.0) |
| `Приборная панель/` | Исходники дизайна (в т.ч. макет `Group 57.png`) |
| `образ для nanoPC-T6/` | Образы ОС для устройства (в git не хранятся) |

## Сборка

Нужен Qt 6.8+ с модулями Quick и WebView.

```bash
cmake -S Dashboard -B build -DCMAKE_BUILD_TYPE=Release
cmake --build build -j4
```

## Запуск

```bash
./build/appDashboard --mock          # демо-режим: данные генерируются, CAN не нужен
./build/appDashboard --can can0      # приём реальных кадров с интерфейса can0
./build/appDashboard --fullscreen    # для установки в автомобиль (без рамки)
```

Отладочный снимок экрана (удобно на устройстве без монитора):

```bash
DASHBOARD_SHOT=/tmp/dash.png ./build/appDashboard --mock
```

## Подготовка CAN на устройстве

```bash
sudo ip link set can0 up type can bitrate 500000
candump can0            # посмотреть, что приходит от ESP32
ip -details link show can0
```

Если интерфейс появится позже запуска приборки, приложение само подключится
к нему в течение 5 секунд. При отсутствии кадров дольше 1,5 с на экране
загорается предупреждение «НЕТ ДАННЫХ CAN».

## Протокол

Версия 1.1, классический CAN, 11-битный ID, 8 байт данных, 500 кбит/с.
Полное описание — `can_protocol_v1.1.txt` (и `CAN_protocol_v1.1.odt`).
Разбор в коде и документация обязаны совпадать: при изменении расположения
данных поднимайте версию протокола и правьте оба места.

| ID | Период | Содержимое |
|---|---|---|
| `0x100` | 50 мс | скорость (байт 0), обороты (байты 1–2, uint16) |
| `0x200` | 50 мс | байт 0 — свет (поворотники, дальний, ближний, габариты, туманки, задний ход, стопы); байт 1 — индикаторы (чек, ABS, ручник, ремень, давление масла, LOCK) |
| `0x300` | 50 мс | температура двигателя, уровень топлива, напряжение ×10, наружная температура (int8), авария по маслу, расход ×10 (uint16, байты 5–6) |
| `0x400` | 50 мс | режим АКПП (P/R/N/D/L), номер передачи, LOCK, провода S1/S2/SL |
| `0x7F0` | 1000 мс | статус блока сбора: счётчик, версия прошивки, время работы, ошибки шины, XOR |

Что исправлено в 1.1 относительно 1.0:

- **Расход топлива не влезал в отведённый байт.** В 1.0 он был объявлен как
  uint8 со значением ×10 при диапазоне 0–99.9 л/100 км, то есть требовал
  0–999. Теперь это uint16 в байтах 5–6.
- **Добавлен кадр 0x7F0.** Без него приборка не могла отличить перезапуск
  блока сбора от зависания: признаки устаревания данных есть, а понять,
  что блок перезапустился, было нечем. Приборка считает перезапуски и
  пишет их в журнал (`deviceRestarts`, `deviceFirmware`, `deviceUptimeSec`).
- Дописаны правила контроля свежести данных и приоритеты ID.

Разбор реализован в `Dashboard/can/CanBackend.cpp` и покрыт тестами:

```bash
cmake -S Dashboard -B build -DDASHBOARD_BUILD_TESTS=ON
cmake --build build --target test_canprotocol
./build/test_canprotocol            # проверки разбора
./build/test_canprotocol --mock-watch   # наблюдение за демо-генератором
```

## Лампы и индикаторы

Все лампы управляются данными из CAN и по умолчанию погашены:

| Лампа | Условие |
|---|---|
| Поворотники | мигают 1,5 Гц, пока приходит соответствующий бит `0x200` |
| Дальний свет, габариты, противотуманки | соответствующие биты `0x200` |
| Ремень | бит «не пристёгнут» `0x200` |
| Ручник | бит ручника `0x200` |
| ABS, Check Engine, давление масла | биты `0x200` |
| Топливо | уровень ≤ 10 % (`0x300`) |
| Зарядка АКБ | двигатель работает (обороты > 400), а напряжение < 12,8 В |
| Перегрев двигателя | температура ≥ 110 °C (`0x300`) |

При включении зажигания все лампы горят 2,5 с (самопроверка), стрелки
проходят полную шкалу.

## Раскладка макета

Экран 1920×720 разбит на зоны (координаты в `Main.qml`):

| Зона | Где | Что там |
|---|---|---|
| Спидометр | x 0…714, y 3…717 | прибор целиком; в навигации — уменьшается до 0.5 и уходит в левый нижний угол |
| Тахометр | x 1206…1920, y 3…717 | прибор целиком; в навигации — уменьшается до 0.5 и уходит в правый нижний угол |
| Верхняя полоса | y 20…75 в центре | часы (x 730), лампы (по центру), наружная температура со снежинкой (x 1080) |
| Верх центра | x 714…1206, y 92…134 | предупреждения: «НЕТ ДАННЫХ CAN» и «ГОЛОЛЁД» |
| Центр | x 714…1206, y 154…558 | переключаемые режимы (`CenterPanel.qml`): стандарт / компьютер / диагностика, внизу точки-индикаторы. Позже сюда же встанет 3D-модель |
| Низ центра | x 714…1206, y 566…650 | показания (напряжение, топливо, температура, расход) и одометр |
| Цифровые значения | внутри каждого прибора, y 230…306 | цифровая скорость и цифровые обороты над ступицей, без подписей единиц |

**Про цифры в приборах.** Свободная полоса на циферблате — ровно 79 px прямо над
ступицей (y 230…306): сверху её подпирает иконка ремня (заканчивается на y=228),
снизу — иконка передачи (начинается с y=307). Выше ставить нельзя: там ходят
стрелки, причём не только основная, но и топлива с температурой — они той же
длины, что и спидометр.

Цифры нарисованы **поверх стрелок** и отделены от них тонким чёрным контуром
(`style: Text.Outline`): стрелка тахометра проходит через цифры на ~4000 об/мин,
и без контура белые цифры сливались бы со светлой стрелкой. Появляются они
**после самопроверки** приборов (первые 2,5 с скрыты), как в серийных панелях.

Важно, почему приборы уменьшаются и уходят в нижние углы в навигации:
**циферблаты полупрозрачные** (альфа 255 только в центре, на радиусе 300 — уже
16). На чёрном фоне это не видно, но поверх карты приборы просвечивают и
становятся нечитаемы. Поэтому в навигации карта занимает весь экран, приборы
уменьшаются до 0.5 и уезжают в нижние углы, а под каждым прибором ставится
непрозрачная чёрная подложка. Верхний и нижний край карты затемняются
градиентом, чтобы лампы, часы и строка показаний читались поверх карты.

Линии-разделители — картинки 641×5 (натуральный размер, не растягивать).
В раскладке они шириной 800 с центром на середине: концы заходят под приборы,
как в макете дизайнера.

Значки шкал (топливо и температура двигателя) — часть разметки прибора, они
видны всегда. Мигают только при низком уровне топлива или перегреве.

## Центральная зона: режимы

Центр (492×404) не пытается показать всё сразу — там переключаемые режимы,
как в iDrive. Переключение — нажатием по центру или клавишами (пробел, стрелки).
Внизу точки-индикаторы.

| Режим | Что показывает |
|---|---|
| Стандарт | крупная цифровая скорость, передача, часы |
| Компьютер | средний расход, запас хода, средняя скорость, время в пути, пробег и литры за поездку |
| Диагностика | блок сбора: версия прошивки, время работы, перезапуски, ошибки шины, принятые кадры, интерфейс, свежесть данных |

Одиночное нажатие ждёт 220 мс, иначе двойной клик (окно калибровки) успевал бы
заодно переключить режим. Долгое нажатие — навигация.

### Маршрутный компьютер

Считается в `CanBackend` по пробегу и мгновенному расходу:

- путь и литры копятся на каждом кадре `0x100`, а в QML отдаются **раз в секунду** —
  чаще незачем, а перерисовка текста 20 раз в секунду только грузит приборку;
- средний расход = литры ÷ путь × 100, показывается только после 0,5 км (раньше
  это случайные числа);
- запас хода = остаток топлива в литрах ÷ средний расход;
- средняя скорость = путь ÷ время поездки, поэтому на стоянке она падает —
  время идёт, путь нет.

Проверено на демо-генераторе: за минуту поездки путь 0.679 км, израсходовано
0.058 л, средний расход 8.5 л/100 (в демо мгновенный гуляет 8.1–8.9), запас хода
543 км при 77 % бака и 60 л.

## Геометрия стрелок и шкал

Замерено по исходникам дизайнера — это нужно для любой правки приборов.

**Стрелки.** Все четыре стрелки (`needls_spd/fuel/temp/tho.svg`) — один и тот же
рисунок, и при `rotation = 0` он смотрит **не вверх, а влево, примерно на 191°**.
Поэтому угол поворота считается как `угол_метки_на_шкале − 191.2`:

| Прибор | Угол стрелки = 191.2 + rotation | В коде |
|---|---|---|
| Спидометр, 0 км/ч | метка «0» на 135.1° | `speedStartAngle: -56.1` |
| Спидометр, 220 км/ч | метка «220» на 20.3° | `speedEndAngle: 189.1` |
| Тахометр, 0 об/мин | метка «0» на 134.5° | `rpmStartAngle: -56.7` |
| Тахометр, 8000 об/мин | метка «8» на 46.1° | `rpmEndAngle: 214.9` |

Метки шкалы спидометра стоят через 22.29° (по 20 км/ч), метки тахометра — через
33.5° (по 1000 об/мин), «4» тахометра ровно вверху (269.8°).

Если правите углы — проверяйте так: запустите `./appDashboard` без `--mock`,
CAN-данных нет, все значения нулевые, стрелки должны стоять ровно на нулях шкал.

## Коэффициенты калибровки

Двойной клик по центральной области открывает окно калибровки (скорость,
обороты, топливо, температура). Значения сохраняются и применяются при запуске.
Долгое нажатие по центральной области — режим навигации (карта).
Долгое нажатие на одометре — сброс текущего trip.

## Что ещё не сделано

- **Прошивки ESP32 нет.** В репозитории есть протокол и проверенная таблица
  пинов, но самого кода блока сбора пока нет.
- Автозапуск, kiosk-режим и настройка SocketCAN на устройстве.
- Навигация работает на внешней карте OpenStreetMap и требует интернета;
  офлайн-карты не подключены.
- Нет экрана диагностики: состояние блока сбора (версия прошивки, время
  работы, перезапуски, ошибки шины) отдаётся в QML, но не показывается.

## Что было исправлено в документации

Протокол и таблица пинов приведены в соответствие с железом:

- Расход топлива в `0x300` не помещался в uint8 при заявленном диапазоне
  0–99.9 л/100 км ×10 → перенесён в uint16 (байты 5–6), версия протокола 1.1.
- Добавлен кадр статуса блока сбора `0x7F0` и правила контроля свежести данных.
- В таблице пинов были занятые флешем GPIO 6–11, несуществующие GPIO 20/24,
  аналоговые входы на не-АЦП выводах 21/22, входы на strapping-выводах,
  и делитель 10к/3.3к, который при 14.5 В даёт 3.60 В — на пределе
  абсолютного максимума для вывода ESP32. Не было согласования CAN 120 Ом.

## Важные особенности реализации

- CAN читается **напрямую через SocketCAN** (`PF_CAN`/`SOCK_RAW`), без
  `Qt6::SerialBus`: этого модуля нет в системе разработки и он может
  отсутствовать на nanoPC-T6, а формат кадра у нас фиксированный —
  классический CAN, 11-битный ID, 8 байт. Дополнительных зависимостей
  на устройстве не требуется, достаточно поддержки SocketCAN в ядре.
- `CanBackend` — QML-синглтон. Его конструктор **намеренно объявлен без
  аргумента по умолчанию**: Qt при регистрации синглтона сначала проверяет
  возможность создать объект конструктором по умолчанию и только потом —
  статический `create()`. Если класс default-constructible, QML создаст второй
  экземпляр, и данные в приборку не попадут (молча, без ошибок в логе).
- Анимации стрелок пишут в отдельное свойство `sweepAngle`, а не в `rotation`:
  запись в привязанное свойство разрушает привязку, и стрелка «застывает».
- Абсолютных путей к файлам быть не должно — только ресурсы QML-модуля.
