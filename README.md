# Приборная панель (Audi Dashboard)

Виртуальная приборная панель для автомобиля: Qt6/QML-интерфейс на nanoPC-T6 (RK3588),
данные приходят по CAN от блока сбора на ESP32.

```
ESP32 (сбор сигналов)  ──CAN 500 кбит/с──►  nanoPC-T6 (SocketCAN)  ──►  Qt6/QML приборка
```

## Структура

| Путь | Что это |
|---|---|
| `Dashboard/` | Приложение Qt6/QML |
| `Dashboard/Main.qml` | Компоновка макета 1920×720, привязка данных к бэкенду |
| `Dashboard/Speedometer.qml`, `Tachometer.qml` | Приборы (стрелки, шкалы) |
| `Dashboard/Indicators.qml` | Лампы, часы, одометр/trip |
| `Dashboard/Settings.qml` | Настройки приборки: коэффициенты показаний и ввод пробега при замене панели (оверлей, кнопка «Настройки») |
| `Dashboard/MapWebView.qml` | Карта (OpenStreetMap) в режиме навигации |
| `Dashboard/can/CanBackend.*` | Приём CAN, разбор протокола, демо-режим || `Dashboard/tests/` | Тест разбора протокола |
| `can_protocol_v1.2.txt`, `CAN_protocol_v1.2.odt` | Описание CAN-протокола (версия 1.2) |
| `esp32_wiring.txt` | Таблица подключения сигналов к ESP32 (версия 2.0) |
| `Приборная панель/` | Исходники дизайна (в т.ч. макет `Group 57.png`) |
| `образ для nanoPC-T6/` | Образы ОС для устройства (в git не хранятся) |

## Сборка

Нужен Qt 6.8+ с модулями Quick и WebView.

```bash
cmake -S Dashboard -B build -DCMAKE_BUILD_TYPE=Release
cmake --build build -j4
```

## Запуск

Самый простой путь — скрипт `run.sh` (собирает, если нужно, и запускает):

```bash
./run.sh                        # в машине: CAN can0, полный экран
./run.sh --window --mock        # на столе: окно и демо-данные
./run.sh --mock --city 56.8052,60.6512   # демо-маршрут в своём городе
./run.sh --mock --demo-camera 20 --demo-type 102   # сразу камера впереди
./run.sh --shot /tmp/dash.png --mock --shot-delay 12000   # снимок и выход
./run.sh --help                 # все ключи
```

Напрямую, без скрипта:

```bash
./build/appDashboard --mock          # демо-режим: данные генерируются, CAN не нужен
./build/appDashboard --can can0      # приём реальных кадров с интерфейса can0
./build/appDashboard --fullscreen    # для установки в автомобиль (без рамки)
```

### Заставка при запуске

При старте приборка показывает ролик `Dashboard/media/startup_intro.mp4`
(47 с, 1918×734, без звука) во весь экран: он лежит в ресурсах, поэтому
работает и на устройстве. Ролик запускается после первого отрисованного кадра,
играет один раз; по окончании приборка переходит в штатный режим (приборы,
самопроверка ламп). Пропустить — клик в любом месте, `Esc` или `Space`.
Страховочный таймер закрывает заставку через 55 с, если что-то пошло не так.
Отключить совсем: `./build/appDashboard --no-intro`.

Звук у ролика отключён (`audioOutput: null`): приборка в машине не должна
гудеть при включении.

Полезные переменные окружения (их же подставляет `run.sh`):

| Переменная | Что делает |
|---|---|
| `DASHBOARD_SHOT` / `DASHBOARD_SHOT_DELAY` | снимок окна в файл и выход (для устройства без монитора) |
| `DASHBOARD_DEMO_CAMERA` | демо-камера в 420 м впереди (значение — ограничение км/ч) |
| `DASHBOARD_DEMO_CAMERA_TYPE` | код типа демо-точки (1 камера, 102 неровность, 22 переход…) |
| `DASHBOARD_MOCK_LAT` / `DASHBOARD_MOCK_LON` | перенести демо-маршрут в свой город |
| `DASHBOARD_SPEEDCAM` | путь к базе камер (иначе ищется автоматически) |

Отладочный снимок экрана напрямую:

```bash
DASHBOARD_SHOT=/tmp/dash.png ./build/appDashboard --mock
```

## Подготовка CAN на устройстве

```bash
sudo ip link set can0 up type can bitrate 500000
candump can0            # посмотреть, что приходит от ESP32
ip -details link show can0
```

Если интерфейс появится позже запуска приборки, приложение само подключится
к нему в течение 5 секунд. При отсутствии кадров дольше 1,5 с на экране
загорается предупреждение «НЕТ ДАННЫХ CAN».

## Протокол

Версия 1.2, классический CAN, 11-битный ID, 8 байт данных, 500 кбит/с.
Полное описание — `can_protocol_v1.2.txt` (и `CAN_protocol_v1.2.odt`).

| ID | Период | Содержимое |
|---|---|---|
| `0x100` | 50 мс | скорость (байт 0), обороты (байты 1–2, uint16) |
| `0x200` | 50 мс | байт 0 — свет (поворотники, дальний, ближний, габариты, туманки, задний ход, стопы); байт 1 — индикаторы (чек, ABS, ручник, ремень, давление масла, LOCK) |
| `0x300` | 50 мс | температура двигателя, уровень топлива, напряжение ×10, наружная температура (int8), авария по маслу, расход ×10 (uint16, байты 5–6) |
| `0x400` | 50 мс | режим АКПП (P/R/N/D/L), номер передачи, LOCK, провода S1/S2/SL |
| `0x500` | 200 мс | газовое оборудование: флаги (работа на газе, исправность датчика), напряжение датчика уровня газа 0…5 В (uint16, мВ) |
| `0x7F0` | 1000 мс | статус блока сбора: счётчик, версия прошивки, время работы, ошибки шины, XOR |

Что нового в 1.2:

- **Кадр `0x500` — газовое оборудование.** Машина двухтопливная: блок сбора
  отдаёт признак «едем на газе» и сырое напряжение датчика уровня газа 0…5 В,
  а проценты (0 В — пусто, 5 В — полный) считает приборка, чтобы кривую под
  свой датчик можно было задать в настройках панели.
- На газу значок бензоколонки на шкале спидометра становится зелёным, а в
  нижней строке показаний вместо литров бензина выводится «газ N %».

Что исправлено в 1.1 относительно 1.0:

- **Расход топлива не влезал в отведённый байт.** В 1.0 он был объявлен как
  uint8 со значением ×10 при диапазоне 0–99.9 л/100 км, то есть требовал
  0–999. Теперь это uint16 в байтах 5–6.
- **Добавлен кадр 0x7F0.** Без него приборка не могла отличить перезапуск
  блока сбора от зависания: признаки устаревания данных есть, а понять,
  что блок перезапустился, было нечем. Приборка считает перезапуски и
  пишет их в журнал (`deviceRestarts`, `deviceFirmware`, `deviceUptimeSec`).
- Дописаны правила контроля свежести данных и приоритеты ID.

Разбор реализован в `Dashboard/can/CanBackend.cpp` и покрыт тестами:

```bash
cmake -S Dashboard -B build -DDASHBOARD_BUILD_TESTS=ON
cmake --build build --target test_canprotocol
./build/test_canprotocol            # проверки разбора
./build/test_canprotocol --mock-watch   # наблюдение за демо-генератором
```

## Лампы и индикаторы

Все лампы управляются данными из CAN и по умолчанию погашены:

| Лампа | Условие |
|---|---|
| Поворотники | мигают 1,5 Гц, пока приходит соответствующий бит `0x200` |
| Дальний свет, габариты, противотуманки | соответствующие биты `0x200` |
| Ремень | бит «не пристёгнут» `0x200` |
| Ручник | бит ручника `0x200` |
| ABS, Check Engine, давление масла | биты `0x200` |
| Топливо | уровень ≤ 10 % (`0x300`) |
| Зарядка АКБ | двигатель работает (обороты > 400), а напряжение < 12,8 В |
| Перегрев двигателя | температура ≥ 110 °C (`0x300`) |

**Запас хода до заправки.** Приборка считает его сама: средний расход за
последние 5 минут (окно 300 сэмплов по секунде) и остаток топлива в литрах
(уровень × объём бака из настроек, по умолчанию 60 л). Запас = остаток ÷ расход
× 100 и показывается на экране «Компьютер» строкой «Запас хода ~320 км».
Когда средний расход меньше 0,1 л/100 км (машина стоит), показывается последнее
достоверное значение — цифра не мигает и не показывает фантастические
километры. Если запас меньше 50 км, в верхней зоне центра загорается жёлтая
надпись «ЗАПРАВКА N КМ», а меньше 20 км — красная и мигает 1 Гц.

**Машина двухтопливная (бензин и газ).** На газу (кадр `0x500`) значок
бензоколонки на шкале спидометра становится зелёным, в нижней строке показаний
вместо литров бензина выводится «газ N %», а в правом верхнем углу монетки
сыплются в кошелёк — газ дешевле, «экономим». Выше 5000 об/мин вместо монеток
появляется топка, в которую кочегар бросает пачки денег. Проценты приборка
считает сама из напряжения датчика уровня газа: 0 В — пустой баллон, 5 В —
полный. Если датчик не отвечает — вместо числа прочерк.

Пока прошивки блока сбора нет, режим газа можно включить **отладочной кнопкой
«Газ: вкл/выкл»** на панели (она перекрывает признак из CAN) или дождаться
демо-режима: в `--mock` газ включается с 15-й по 45-ю секунду каждой минуты.
Рядом кнопка **«Газ в пол»** — она принудительно ставит 5400 об/мин, чтобы
посмотреть кочегара с пачками денег, не дожидаясь всплеска в демо-сценарии.

При включении зажигания все лампы горят 2,5 с (самопроверка), стрелки
проходят полную шкалу.

## Раскладка макета

Экран 1920×720 разбит на зоны (координаты в `Main.qml`):

| Зона | Где | Что там |
|---|---|---|
| Спидометр | x 0…714, y 3…717 | прибор целиком; в навигации — уменьшается до 0.5 и уходит в левый нижний угол |
| Тахометр | x 1206…1920, y 3…717 | прибор целиком; в навигации — уменьшается до 0.5 и уходит в правый нижний угол |
| Верхняя полоса | y 20…75 в центре | часы (x 730), лампы (по центру) |
| Правый верхний угол | x ~1650…1840, y 8…158 | анимация газа: монетки сыплются в кошелёк, а выше 5000 об/мин — кочегар бросает пачки денег в топку (угол свободен: циферблат тахометра кончается левее) |
| Верх центра | x 714…1206, y 92…134 | предупреждения: «НЕТ ДАННЫХ CAN» и «ГОЛОЛЁД» |
| Центр | x 714…1206, y 154…558 | переключаемые режимы (`CenterPanel.qml`): стандарт / компьютер / диагностика / напряжение / **машина** / подвеска / **климат** / **медиа**, внизу точки-индикаторы |
| Низ центра | x 714…1206, y 566…650 | показания (напряжение, топливо или «газ N %» на газу, температура, расход) и одометр |
| Цифровые значения | внутри каждого прибора, y 230…306 | цифровая скорость и цифровые обороты над ступицей, без подписей единиц |

**Про цифры в приборах.** Свободная полоса на циферблате — ровно 79 px прямо над
ступицей (y 230…306): сверху её подпирает иконка ремня (заканчивается на y=228),
снизу — иконка передачи (начинается с y=307). Выше ставить нельзя: там ходят
стрелки, причём не только основная, но и топлива с температурой — они той же
длины, что и спидометр.

Цифры нарисованы **поверх стрелок** и отделены от них тонким чёрным контуром
(`style: Text.Outline`): стрелка тахометра проходит через цифры на ~4000 об/мин,
и без контура белые цифры сливались бы со светлой стрелкой. Появляются они
**после самопроверки** приборов (первые 2,5 с скрыты), как в серийных панелях.

Важно, почему приборы уменьшаются и уходят в нижние углы в навигации:
**циферблаты полупрозрачные** (альфа 255 только в центре, на радиусе 300 — уже
16). На чёрном фоне это не видно, но поверх карты приборы просвечивают и
становятся нечитаемы. Поэтому в навигации карта занимает весь экран, приборы
уменьшаются до 0.5 и уезжают в нижние углы, а под каждым прибором ставится
непрозрачная чёрная подложка. Верхний и нижний край карты затемняются
градиентом, чтобы лампы, часы и строка показаний читались поверх карты.

Линии-разделители — картинки 641×5 (натуральный размер, не растягивать).
В раскладке они шириной 800 с центром на середине: концы заходят под приборы,
как в макете дизайнера.

Значки шкал (топливо и температура двигателя) — часть разметки прибора, они
видны всегда. Мигают только при низком уровне топлива или перегреве.

## Центральная зона: режимы

Центр (492×404) не пытается показать всё сразу — там переключаемые режимы,
как в iDrive. Переключение — нажатием по центру или клавишами (пробел, стрелки).
Внизу точки-индикаторы.

| Режим | Что показывает |
|---|---|
| Стандарт | крупная цифровая скорость, передача |
| Компьютер | средний расход, запас хода (~N км — по среднему расходу за последние 5 минут), средняя скорость, время в пути, пробег и литры за поездку |
| Диагностика | блок сбора: версия прошивки, время работы, перезапуски, ошибки шины, принятые кадры, интерфейс, свежесть данных |
| Напряжение | график напряжения АКБ за последние 5 минут: ось Y 10…15 В, зоны < 11.5 В красная, 11.5…12.8 жёлтая, > 12.8 зелёная |

Одиночное нажатие ждёт 220 мс, иначе двойной клик (вход в настройки) успевал бы
заодно переключить режим. Долгое нажатие — навигация.

### Настройки

Кнопка **«Настройки»** внизу центральной полосы (или двойной клик по центру)
открывает экран настроек: множители показаний (скорость, обороты, топливо,
температура), **ввод пробега** — показание старой приборки при замене панели,
**объём бака** (нужен для расчёта запаса хода) — и переключатели **«Приколы»**
(анимация в правом верхнем углу: монетки в кошелёк на газу и кочегар с пачками
денег выше 5000 об/мин) и **«Погода»** (дождь/снег на панели). Введённый пробег и объём бака принимает `CanBackend`
и сразу сохраняет в `QSettings`, коэффициенты и выключатель приколов хранит
`Settings.qml`. Ввод с клавиатуры: Esc — отмена, Enter — сохранить.

Это оверлей внутри главного окна, а не отдельное окно: на устройстве приборка
работает через EGLFS, который поддерживает только одно окно.

### 3D-машина и запуск приборки

При запуске приборка открывается в **5-м виде «машина»** и в нём остаётся:
пока панель не прогрузилась, на экране только модель (без дороги). Затем
появляется дорога (две полосы разметки, уходящие в даль, концы — под
горизонтальные полосы у приборов, штрихи «едут» к зрителю), из глубины
выезжает машина, камера смотрит чуть сверху (~30°), в конце она
разворачивается кормой. Пока на экране машина — **никаких данных**: приборы
проявляются на 3–4 с (стрелки проходят шкалу), но их вид пользователь
выбирает сам щелчком по центру (0→1→2→3→4→0). В навигации машина скрыта.
На модели включаются **фары и задние фонари** (по CAN: ближний/габариты),
на дороге перед ней — лёгкое пятно света, а **поворотники** мигают вместе с
лампой на панели. В `--mock` это происходит само по циклу: свет загорается
через ~3 с, левый поворотник мигает на 12–18 с, правый — на 28–34 с.
Это каркас: настоящую модель (двери, колёса, анимации) дизайнер пока готовит.

Нужно одно условие: модуль `qml6-module-qtquick3d` (идёт с Qt) и рабочий
OpenGL/GLES — QtQuick3D рисует только через RHI. Модель — белый
**cruiser300** (`cruiser300.glb` в корне проекта): `tools/bake_glb.py`
запекает мировые трансформации в вершины, `balsam` собирает готовую
сцену `Dashboard/CarModel.qml` + `Dashboard/assets/cruiser/` (`.mesh` +
WebP-атлас). В рантайме это обычный QML-компонент модуля — никаких
импортёров. Три ловушки Qt Quick 3D, на которые уже потрачены часы
(подробно — `PROJECT_STATE.md`): рантайм-импорт glTF (`RuntimeLoader`)
«успешен», но с испорченной геометрией; **`Loader` не привязывает 3D-узел
к сцене** (машина не рисуется) — только прямое объявление компонента;
**`PerspectiveCamera.clipNear` по умолчанию 10** — всё ближе 10 единиц
отсекается, поэтому камера обязана ставить `clipNear: 0.5`.

Пересобрать 3D-активы (balsam — только на машине разработки):

```bash
sudo apt install qt6-quick3d-dev-tools
python3 tools/bake_glb.py cruiser300.glb /tmp/cruiser_baked.glb
balsam /tmp/cruiser_baked.glb -o /tmp/cruiser_out/
# потом: CarModel.qml из /tmp/cruiser_out/Cruiser_baked.qml, пути →
# assets/cruiser/..., к Model добавить scale: 0.001 (модель в см)
```

Отключить заставку и 3D-машину: `./appDashboard --no-3d`.

### Погода: дождь и снег на панели

Если на улице дождь или снег, на приборке идёт дождь/снег — как на стекле.
Источник — `WeatherProvider` (Open-Meteo, бесплатный API без ключа): запрос
раз в 10 минут по координатам из `QSettings` (`weather/latitude`,
`weather/longitude`; по умолчанию Москва). Состояния: ясно/облачно/туман/
дождь/снег; дождь и снег рисуются слоем **поверх приборов** (они непрозрачные
и иначе перекрыли бы эффект) с прозрачностью 0.55. Без интернета эффекта нет
— приборка работает как обычно. В `--mock` состояния меняются по кругу раз
в 8 секунд (дождь → снег → ясно), чтобы можно было проверить без сети.

### Камеры (Smart Driver)

Предупреждение о камерах и дорожных опасностях по базе OpenSpeedcam —
поддерживаются обе выгрузки: компактный iGO `speedcam.txt` и PocketGIS как
есть (IDX,X,Y,TYPE,..., ~200 тысяч точек, Windows-1251). Позиция приходит по CAN (кадры 0x520/0x521),
расстояние считается по гаверсинусу в `SpeedCamManager`
(`Dashboard/speedcam/`), показывается баннер `CameraWarning.qml` в верхней
полосе между приборами.

Вид баннера — по схеме «знак — стрелочка — сколько осталось», без рамки и без
названия комплекса (лишнего на приборке не нужно):

```
 ( 60 )  ▶▶  350 м
```

- знак ограничения — как настоящий дорожный: белый круг, красная обводка,
  чёрное число (у трёхзначных вроде 110 шрифт мельче); значения 10…130 км/ч;
- стрелки ▶▶▶▶▶▶ показывают направление, дальше крупно — сколько метров
  осталось; по мере приближения галочки гаснут по одной слева, последняя
  всегда указывает на оставшиеся метры;
- пока скорость в пределах ограничения, расстояние просто уменьшается по мере
  подъезда; при превышении всё краснеет и **знак пульсирует** (мигает только
  знак — цифры остаются читаемыми);
- висит под верхней полосой, над машиной (y≈160), и не перекрывает модель;
- при появлении новой точки — короткий бип.

- база читается в фоновом потоке (207 тысяч точек PocketGIS — ~2 с, интерфейс
  при этом живой); поиск идёт по сетке ~2 км, а не перебором всех точек;
- из PocketGIS берутся название типа и модель комплекса («Кордон», «Стрелка+»,
  «Автоураган»), а также своя дистанция предупреждения (`DISTANCE`): к
  «лежачему полицейскому» приборка предупреждает за 100 м, к камере — за 500;
- камера, оставшаяся позади (дальше ±100° от курса), предупреждение снимает;
  направленные камеры (`DIRTYPE=1`) срабатывают только на свой поток;
- что вообще бывает в базе (типы, ограничения, дистанции, модели) —
  `docs/speedcam_stats.md`, пересчитывается `tools/speedcam_stats.py`;
- обновление базы — `update_speedcam.sh` раз в сутки (systemd timer,
  юниты в `deploy/systemd/`), подробности и способы получить файл —
  в `docs/speedcam.md`. Открытых ссылок у OpenSpeedcam нет: их экспорт
  требует авторизации, поэтому скрипт берёт файл по вашей личной ссылке,
  из публичного зеркала или с диска (`--file`);
- кнопка «Симулировать камеру» в настройках (или клавиша `C`, или
  `DASHBOARD_DEMO_CAMERA=60`) ставит демо-камеру в 420 м впереди — так
  предупреждение проверяется без реальной базы и без поездки.

### График напряжения АКБ

Режимы центральной зоны листаются щелчком: стандарт → компьютер →
диагностика → напряжение → **машина** (5-й вид: без данных, только 3D-модель).

Отдельный режим центральной зоны («Напряжение»): график за последние 5 минут.
`CanBackend` хранит кольцевой буфер на 300 замеров (по одному в секунду) и
отдаёт его в QML списком от старых к новым; замеры, когда кадров нет, приходят
как `NaN` — на графике это разрыв, а не выдуманное значение. Ось Y 10…15 В,
зоны: меньше 11.5 В — красная, 11.5…12.8 — жёлтая, больше 12.8 — зелёная;
отрезки линии красятся по своему значению. Рисуется на `Canvas` и
перерисовывается только по приходу нового замера (раз в секунду), а не каждый
кадр — поэтому график не отнимает кадры у приборов (замер — в `PROJECT_STATE.md`,
раздел «Производительность графиков»).

### Маршрутный компьютер

Считается в `CanBackend` по пробегу и мгновенному расходу:

- путь и литры копятся на каждом кадре `0x100`, а в QML отдаются **раз в секунду** —
  чаще незачем, а перерисовка текста 20 раз в секунду только грузит приборку;
- средний расход = литры ÷ путь × 100, показывается только после 0,5 км (раньше
  это случайные числа);
- запас хода = остаток топлива в литрах ÷ средний расход;
- средняя скорость = путь ÷ время поездки, поэтому на стоянке она падает —
  время идёт, путь нет.

Проверено на демо-генераторе: за минуту поездки путь 0.679 км, израсходовано
0.058 л, средний расход 8.5 л/100 (в демо мгновенный гуляет 8.1–8.9), запас хода
543 км при 77 % бака и 60 л.

### Покраска 3D-модели

Цвет машины на приборке задаётся материалами в GLB. Кузов — материал
`base white` (отдельного «крыши» нет), поэтому покраска делается скриптом:

```bash
python3 tools/paint_model.py --list                    # какие материалы есть
python3 tools/paint_model.py --body "#1E2A44" --out /tmp/car_blue.glb
python3 tools/paint_model.py --body "#1E2A44" --wheel "#2A2E33" \
        --out Dashboard/assets/ipsum_fin.glb           # покрасить на месте
```

Материалы: `base white` кузов · `black glossy` молдинги · `inside black` салон ·
`red` фонари · `black glass` стёкла · `orange`/`orange glass` поворотники и
фары · `metallic` хром · `wheel` шины. Скрипт меняет только
`baseColorFactor` (и, если нужно, металличность/шероховатость), геометрию не
трогает, поэтому двери и анимации продолжают работать.

Отдельные части кузова (крыша, решётка, спойлеры) красятся вторым скриптом —
в модели это один материал, поэтому их выкраивают из меша в свой материал:

```bash
python3 tools/paint_parts.py --list
python3 tools/paint_parts.py --roof "#3B2A22" --grille "#3B2A22" \
        --spoiler "#3B2A22" --out Dashboard/assets/ipsum_fin.glb
```

Правила выкраивания заданы координатами модели (метры, нос в +Z, низ кузова
Y≈2.0, крыша Y≈3.72) и вынесены в ключи: `--roof-level` (3.50), `--grille-z`
(4.00), `--spoiler-level` (3.05). Если часть «уехала» — достаточно поправить
порог, геометрия не портится: новый примитив использует те же вершины и лишь
свой список индексов.

Текущая раскраска: кузов `#F7F5F0` (белый перламутр, metallic 0.25,
roughness 0.5 — полуматовый лак), крыша/решётка/спойлеры `#3B2A22`
(тёмно-коричневый металлик, metallic 0.85, roughness 0.30), стёкла — тонировка
`#0A0C10` с прозрачностью 0.5 (`alphaMode: BLEND`), в тот же материал входят
оба люка в крыше.

Вся цепочка собирается одной командой (кузов → крыша и спойлеры → решётка →
тонировка → петли):

```bash
./tools/repaint_car.sh                        # из ~/Документы/main_3.3.glb
./tools/repaint_car.sh путь/к/модели.glb      # из другого файла
```

### Поворотники на модели

Поворотник в модели живёт в трёх местах, и все три мигают от одного сигнала:

| Узлы | Что это | Примитив с поворотником |
|---|---|---|
| 9, 10 | фары: кусок в крыле до капота | материал `orange glass`, индекс 1 |
| 7, 8 | задние фонари | материал `orange`, индекс 0 |
| 11, 12 | отдельные маленькие узлы (4 см) | единственный примитив |

Материалы у них родные и общие с другими деталями, поэтому каждому месту при
загрузке подставляется свой `PrincipledMaterial`, а мигание делается через
`emissiveFactor`: включено — `Qt.vector3d(1, 0.5, 0)`, выключено — ноль. Фаза берётся из `turnBlink` в `Main.qml` (одна на панель и
модель, 333 мс ≈ 1.5 Гц), поэтому стрелка на приборке и огонь на машине
мигают синхронно. Плюс на местах огней горит мягкое свечение: два плоских «блина» с радиальной
текстурой `images/turn_glow.png` (длинный плавный хвост, без резкой границы) —
один крупный ореол, второй плотнее и меньше, чтобы центр читался. Шаров и
жёстких ядер нет: из-за них огонь выглядел как шарик, а не как свет. Сами узлы
модели по 4 см — на экране это 2–3 пикселя, их свечения не увидеть. Маркеры стоят в координатах
модели (у «запечённой» выгрузки они другие — если машина подменяется, Y
маркеров надо пересчитывать: один раз они уехали на 2 м ниже кузова и
«ничего не мигало»).

Проверить без клавиатуры: `DASHBOARD_DEMO_TURN=left` (или `right`)
`./build/appDashboard --mock`.

### Петли подвижных частей

В выгрузке дизайнера (`main_3.3.glb`) трансформации «запечены» в вершины: у
узлов нет ни `translation`, ни `rotation`, поэтому геометрия двери лежит в
мировых координатах, а точка вращения — в центре машины. Повернуть такую
дверь — значит «улетит через всю машину». Скрипт `tools/restore_pivots.py`
считает петлю по габаритам детали, сдвигает вершины и прописывает узлу
`translation` — после этого поворот идёт вокруг петли:

| Часть | Петля |
|---|---|
| Двери (4 шт.) | передняя кромка двери |
| Капот | задняя кромка, у лобового стекла |
| Задняя дверь | верхняя кромка |
| Колёса | центр колеса |

Проверка: поворот двери на 45° смещает её центр на 0.45 м (наружу), капота
на 35° — на 0.34 м (кромка вверх), задней двери на 55° — на 0.54 м (вверх и
назад), колёс — на 0.00 м (крутятся вокруг своей оси).

## Геометрия стрелок и шкал

Замерено по исходникам дизайнера — это нужно для любой правки приборов.

**Стрелки.** Все четыре стрелки (`needls_spd/fuel/temp/tho.svg`) — один и тот же
рисунок, и при `rotation = 0` он смотрит **не вверх, а влево, примерно на 191°**.
Поэтому угол поворота считается как `угол_метки_на_шкале − 191.2`:

| Прибор | Угол стрелки = 191.2 + rotation | В коде |
|---|---|---|
| Спидометр, 0 км/ч | метка «0» на 135.1° | `speedStartAngle: -56.1` |
| Спидометр, 220 км/ч | метка «220» на 20.3° | `speedEndAngle: 189.1` |
| Тахометр, 0 об/мин | метка «0» на 134.5° | `rpmStartAngle: -56.7` |
| Тахометр, 8000 об/мин | метка «8» на 46.1° | `rpmEndAngle: 214.9` |

Метки шкалы спидометра стоят через 22.29° (по 20 км/ч), метки тахометра — через
33.5° (по 1000 об/мин), «4» тахометра ровно вверху (269.8°).

Если правите углы — проверяйте так: запустите `./appDashboard` без `--mock`,
CAN-данных нет, все значения нулевые, стрелки должны стоять ровно на нулях шкал.

## Коэффициенты калибровки

Двойной клик по центральной области открывает окно калибровки (скорость,
обороты, топливо, температура). Значения сохраняются и применяются при запуске.
Долгое нажатие по центральной области — режим навигации (карта).
Долгое нажатие на одометре — сброс текущего trip.

## Что было исправлено в документации

Протокол и таблица пинов приведены в соответствие с железом:

- Расход топлива в `0x300` не помещался в uint8 при заявленном диапазоне
  0–99.9 л/100 км ×10 → перенесён в uint16 (байты 5–6), версия протокола 1.1.
- Добавлен кадр статуса блока сбора `0x7F0` и правила контроля свежести данных.
- В таблице пинов были занятые флешем GPIO 6–11, несуществующие GPIO 20/24,
  аналоговые входы на не-АЦП выводах 21/22, входы на strapping-выводах,
  и делитель 10к/3.3к, который при 14.5 В даёт 3.60 В — на пределе
  абсолютного максимума для вывода ESP32. Не было согласования CAN 120 Ом.

## Важные особенности реализации

- CAN читается **напрямую через SocketCAN** (`PF_CAN`/`SOCK_RAW`), без
  `Qt6::SerialBus`: этого модуля нет в системе разработки и он может
  отсутствовать на nanoPC-T6, а формат кадра у нас фиксированный —
  классический CAN, 11-битный ID, 8 байт. Дополнительных зависимостей
  на устройстве не требуется, достаточно поддержки SocketCAN в ядре.
- `CanBackend` — QML-синглтон. Его конструктор **намеренно объявлен без
  аргумента по умолчанию**: Qt при регистрации синглтона сначала проверяет
  возможность создать объект конструктором по умолчанию и только потом —
  статический `create()`. Если класс default-constructible, QML создаст второй
  экземпляр, и данные в приборку не попадут (молча, без ошибок в логе).
- Анимации стрелок пишут в отдельное свойство `sweepAngle`, а не в `rotation`:
  запись в привязанное свойство разрушает привязку, и стрелка «застывает».
- Абсолютных путей к файлам быть не должно — только ресурсы QML-модуля.
